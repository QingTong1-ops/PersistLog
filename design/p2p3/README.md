# 恒序 persistLog · P2 / P3 页面原型

更新日期：2026-11-15

这是后续工程开发的**页面与交互设计基准**，不是已上线的 P2 / P3 功能。沿用 [P1 页面设计协作规范](../../docs/frontend-design-guidelines.md) 的视觉、布局、动效与文字原则；业务功能参考 [P2 / P3 后端功能接口需求](../../docs/p2p3-backend-requirements.md)，实际技术契约以后端 OpenAPI 为准。

## 预览

从项目根目录启动静态服务：

```bash
python -m http.server 4173 --bind 127.0.0.1
```

打开 `http://127.0.0.1:4173/design/p2p3/index.html`。页面仅依赖原生 HTML、CSS 和 JavaScript，不需要构建，不依赖外部字体、图片或 CDN。

所有页面均使用**预置演示数据**：不上传或执行代码，不调用 AI，不保存账户数据，不创建路线，也不会将简历、回答、任务或错题传给求职平台。其他表单变化只影响当前页面，刷新后恢复。代码文件通过浏览器 `FileReader` 在本地读入编辑区，最大 200 KB，不上传或执行。代码草稿与最后一次异步评审演示仅保存在当前标签页的 `sessionStorage`，关闭标签页后清除；真实接入不能依赖这份会话数据。

## 主流程与验收要点

### P2 · 代码反馈

1. 从当前任务进入网页提交，填写代码、语言、来源、难度、标签、独立性与可选思路。
2. 填写自测通过数、总用例数、失败用例和时间 / 空间复杂度；允许选择“尚未自测”。
3. 每条历史记录整行可点击进入独立详情，待评审、失败、无自测记录也不丢弃代码入口。看板最近提交使用同一详情目标。
4. 通过数不能大于总用例数，行内显示错误。提交成功后进入独立评审页，明确提示“提交成功，正在评审”；进度由已过去的时间驱动，离开后再回到同一 URL 可继续查看。
5. 评审失败必须保留提交内容，允许返回检查或重试。重试追加评审记录，不覆盖旧失败；最新结果与历史评审分开呈现。
6. 桌面端代码在左，评分结果、扣分依据与建议在右，便于同屏对照；代码卡与右侧反馈整体顶底对齐，新增高度用于代码滚动区域，不能只拉伸卡片留白。`1100px` 以下恢复单列。评审中默认展开过程摘要，完成后默认收起，用户可手动切换，刷新不打断展开状态。改进方向、追问和提交历史保留在下方。证据包含文件名、行号与代码片段，点击证据定位代码。改进项最多 3 条，说明改法与验证方法。
7. 未提供自测时，正确性只描述静态风险，不给正确性分；待评审、失败和未评估不进入平均分。
8. 看板时间范围同步更新折线、提交数、平均分、最高分和改进项统计。

固定评审示例：总分 `76`、`B+`、置信度 `0.82`；维度为 `62 / 80 / 74 / 60 / 70`。总分直接采用技术文档示例，不能自行按权重重算。

**边界：**不执行代码、不提供 AC 判定、不测运行时间或内存，不加入沙箱、隐藏测试、CLI、Git 或 IDE。

### P3 · 反馈与记忆

1. **路线生成：**简历 / 目标 / 困境 → 诊断 → 草案 → 调整 → 用户确认。默认 12 周、每日 120 分钟、80% 有效容量，即 `134.4` 小时。演示任务按每项 1.5 小时估计，72 项为 108 小时；96 项为 144 小时，超出 9.6 小时，确认按钮禁用。每日时间或周期改变后，容量、阶段分配和确认摘要同步更新。
2. **确认边界：**生成和确认均不能覆盖执行中路线；局部调整时锁定阶段不可重生成。工程实现需保存草案、版本、用户确认和 AI 授权，而不是直接替换主路线。
3. **每日提问：**每天 3–5 道文字题，本原型选 4 道。空回答显示字段错误，提交后展示预置反馈与追问。进度包含可访问数值，完成后可重访题目。计时可选且可暂停，不自动提交。
4. **错题复习：**默认第 2 / 3 / 7 / 14 / 28 天，最多 10 题 / 天或今日容量的 35%，两者共同限制。先回忆回答再展开参考要点。答错回退一阶段并次日重现；答对但不确定保持当前阶段；答对且确定进阶。
5. **能力看板：**代码 / 工程证据权重 `1.0`，八股 / 项目回答 `0.8`，自评 `0.3`，外部测评 `0.6`；证据时间衰减半衰期 30 天。至少 3 条有效证据且置信度至少 0.5 才评估。准备度只汇总已评估能力，未评估项不画 0 分进度条，也不能被解释为“完全不会”。
6. **复习设置：**间隔必须为递增的正整数，非法输入行内报错；恢复默认后立即还原预览。真实调度需处理已有进度、超额顺延、次日重现与并发保存。

能力示例的准备度为 `70`，证据覆盖率为 `60%`（已评估项的路线权重之和），已评估 `5 / 11` 项，共 `19` 条有效证据。覆盖率不是 `5 ÷ 11`。

## 视觉与领域组件

- 使用 P1 浅色工作区：216px 固定侧栏、60px 顶栏、1360px 最大内容宽度、12px 卡片圆角与克制的靛蓝 / 青绿状态色。
- 桌面主内容必须显式占据 `.app-shell` 第二列；主网格使用 `minmax(0, 1fr)`，代码和图表长内容在自身容器滚动，不能挤压或裁切主内容。
- `860px` 以下切换为顶部品牌 + 页面目录 + 底部导航；`640px` 以下主要内容单列、表单重排、主要触控目标至少 44px；`420px` 以下进一步处理按钮与指标堆叠。主内容底部预留导航空间。
- `prototype.css` 提供卡片、标签、表单、证据行、评分条、错题详情、能力行、时间线、Toast 和原生 `dialog`。React 实现应优先复用 `components/ui.tsx` 与 optimized token，而不是同时维护两套生产样式。
- 原生 `dialog` 用于证据抽屉，需验证 Esc、背景阻断、关闭按钮与焦点恢复。`prefers-reduced-motion` 下压缩动画，内容不能依赖动画才能阅读。
- 原型中 Inline SVG 图标只用于静态预览；工程实现继续使用 `lucide-react`。

## 工程接入约定

1. 先对照后端当期 OpenAPI 定义真实请求与响应，不把 `prototype.js` 中的数据模型当成 API 契约。
2. 所有统计、评分、能力结论、错题阶段与路线版本由真实后端返回；前端不根据静态示例推断分数或持久化调度结果。
3. 用服务端状态驱动加载、空、错误、禁用、重试与完成状态。失败时保留输入，不用 Toast 替代字段错误或高风险确认。
4. 真实异步评审由后端持久化提交、代码快照、任务、进度和评审版本；前端根据后端契约轮询任务状态或订阅 SSE，不用浏览器定时器代替任务状态。提交接口幂等，重试新建评审版本并关联原提交，失败记录不可被覆盖。
5. Agent 读取用户已授权的代码快照与说明，代码访问、第三方发送授权和数据保留策略按后端产品契约实施。界面展示读取范围、处理步骤、扣分原因和代码证据，不伪造逐字思考，也不要求暴露模型内部思维链。
6. P2 代码趋势与 P3 能力证据作为既有 `/dashboard` 的独立区块接入，避免把单次代码得分直接当作能力分。
7. 外部求职平台仅提供固定 URL 跳转，使用 `target="_blank" rel="noopener noreferrer"`，不携带用户数据，不声称已集成平台账户。
8. 不恢复已清理的 P1 静态原型。本目录是 P2 / P3 规划原型，未经真实接口与 React 页面验收，不能写成“功能已实现”。

## 文件

```text
design/p2p3/
├─ index.html
├─ practice.html
├─ practice-detail.html
├─ practice-review.html
├─ code-dashboard.html
├─ route-generate.html
├─ quiz.html
├─ mistakes.html
├─ capability.html
├─ review-settings.html
├─ README.md
└─ assets/
   ├─ prototype.css
   ├─ prototype.js
   └─ practice-review.js
```

`prototype.js` 负责通用外壳和其他 P2 / P3 页面；`practice-review.js` 负责提交历史、代码提交和异步评审演示。`practice-review.js` 必须在 `prototype.js` 之后加载。

静态原型没有引入自动化测试框架。交付前对两个脚本执行 `node --check`，并执行 `pnpm lint`、本地链接检查和浏览器主流程验收；工程实现仍需通过项目标准的 lint、typecheck 和 build。
