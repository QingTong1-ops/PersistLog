## 0. 结论先行

1. **产品本质是执行层，不是 Todo。** 用户不缺题目和课程，缺的是“今天做什么”和“做得怎么样”。
2. **三条闭环**：规划（目标→日计划）、反馈（提交→评分）、记忆（错题→复习）。当前 Phase 1 先打通规划，Phase 2 打通代码反馈，Phase 3 补记忆与完整能力。
3. **Phase 1 不依赖 AI 诊断**：用户导入一份 Markdown 计划即可开始；AI 只负责把计划结构化，不替用户生成路线。
4. **Phase 2 采用方案 A**：代码提交 + AI 静态评审 + 评分趋势；**不执行代码、不做沙箱、不做 CLI/Git/IDE**。正确性只给“静态风险 + 自测通过率”，不冒充 AC 判定。
5. **Phase 1 看板只做执行进度**；Phase 2 加代码评分趋势；Phase 3 才做完整能力/准备度，避免没有证据就打分。
6. **当前不做**：沙箱判题、CLI/IDE、平台数据交换、语音、社区、招聘投递、管理后台。

## 1. 产品定义

### 1.1 一句话

恒序 persistLog 是面向计算机专业求职者的**每日执行与复盘系统**：把计划变成每天可执行的任务，通过企业微信推送驱动执行，用进度看板展示真实进展；后续再接入代码静态评审、错题复习和个性化路线。

### 1.2 要解决的问题

| 现象 | 问题本质 | 恒序的应对 |
|---|---|---|
| 缺乏系统规划 | 目标无法分解为每天的动作 | 计划导入/路线生成 → 阶段/周/日任务 |
| 每日任务缺少对齐度 | 任务与目标没有可追溯关联 | 任务挂阶段/周 + 看板按目标/类型聚合 |
| 每日整理待办繁琐 | 计划维护成本高于执行收益 | 自动生成今日任务 + 推送即入口 |
| 无提醒，不知道做什么 | 缺少稳定触发器和上下文 | 早报/晚报/逾期/顺延/周总结 |
| 想到什么做什么 | 缺少优先级与容量约束 | 每日容量 + 优先级 + 3–6 项上限 |
| 练了不知道有没有变强 | 缺少练习质量反馈 | Phase 2 代码静态评审 + 评分趋势 |
| 错题记了不复习 | 缺少调度机制 | Phase 3 间隔复习 + 自动进今日任务 |
| 简历/困境没人给建议 | 缺少个性化诊断 | Phase 3 AI 诊断 + 路线生成 |

现有工具的问题：通用 Todo 不会拆解和评估；学习平台有内容但没有个人计划；通用 AI 给一次性建议但不跟踪；求职平台不负责每天执行。恒序补的是“执行 + 反馈 + 记忆”这一层。

### 1.3 目标用户

| 画像 | 特征 | 核心诉求 |
|---|---|---|
| 秋招应届（本科/硕士） | 3–6 个月窗口，有 1–2 个项目，表达弱 | 系统规划 + 每日执行 + 面试表达 |
| 社招/转行 | 时间碎片，目标明确但缺方法 | 高效利用 1–2 小时/天 |
| 低年级找实习 | 时间充裕，方向不清 | 探索 + 基础打底 |
| 脱产备考 | 自律要求高，易焦虑 | 节奏 + 反馈 + 陪伴 |

共同点：**有目标、缺拆解；有内容、缺反馈；有错题、缺复习。**

### 1.4 产品边界与非目标

- 不做题库内容生产、社区、私信、导师交易、招聘投递。
- 不做通用笔记/知识管理。
- 不替用户编造简历经历。
- 不做心理诊断或医疗建议；困境分析只限求职相关（技能、表达、时间、信息差、面试反馈）。
- 不用“连续打卡”制造焦虑；展示累计活跃天数。
- 当前不做沙箱判题、CLI/IDE、平台账号打通和数据交换。
- 没有证据的能力一律显示“未评估”，不编造分数。

### 1.5 五条不变决策

1. 不做语音回答。
2. 采用自适应间隔复习（Phase 3 实现，规格已定）。
3. AI 使用第三方 API，不自建/私有化模型。
4. 企业微信推送使用群机器人。
5. 求职平台只做入口链接跳转，不做账号、简历、测评、错题、任务数据交换。

### 1.6 阶段路线

| 阶段 | 目标 | 范围 | 退出标准 |
|---|---|---|---|
| **Phase 1** | 计划能落地 | 导入 Markdown、路线/任务 CRUD、每日计划、今日页、顺延、执行看板、企微推送 | 连续 7 天按计划执行并收到推送 |
| **Phase 2** | 代码有反馈 | 网页提交代码、AI 静态评审、证据/改进/追问、评分趋势 | 每天提交代码能得到可执行反馈 |
| **Phase 3** | 完整闭环 | AI 诊断/路线、八股/项目提问、错题复习、完整能力看板、平台入口 | 产品闭环完整 |

**当前不纳入路线**：沙箱执行/判题、CLI/Git/IDE、语音、QQ/邮件/站内多渠、管理后台、HTML 导入（后续可选增强）。这些不是“永远不做”，而是不作为当前三阶段的承诺。

### 1.7 成功指标

| 阶段 | 指标 | 定义 | 目标 |
|---|---|---|---|
| Phase 1 | 首日激活率 | 完成档案/目标 + 导入/创建路线 + 生成首日计划 | ≥60% |
| Phase 1 | 7 日留存 | 第 7 天仍有执行记录 | ≥40% |
| Phase 1 | 日计划完成率 | 完成 occurrence / 计划 occurrence | ≥65% |
| Phase 1 | 顺延率 | 顺延 occurrence / 计划 occurrence | ≤20% |
| Phase 1 | 推送交互率 | 点击/完成/跳过 / 送达 | ≥30% |
| Phase 2 | 代码提交频次 | 每周提交次数 | ≥3 次/周 |
| Phase 2 | 评审完成率 | 成功评分 / 提交 | ≥95% |
| Phase 2 | 评分趋势 | 最近 30 天均分是否上升 | 观察指标 |
| Phase 3 | 错题复习完成率 | 完成复习 / 到期复习 | ≥75% |
| Phase 3 | 错题掌握率 | 30 天内进入已掌握 | ≥50% |
| Phase 3 | 能力证据覆盖率 | 已评估能力权重 / 总权重 | 观察指标 |

**不作为当前指标**：模拟面试表现、面试机会/Offer 转化——当前没有对应功能，不能假装能统计。

## 2. 总体方案

### 2.1 三条闭环

```text
用户档案 / 计划 / 困境
        ↓
   规划闭环：目标 → 路线 → 阶段 → 周 → 日任务
        ↓
   执行：今日页 / 推送 / 完成 / 顺延
        ↓
   反馈闭环：代码提交 → 静态评审 → 证据/改进/追问
        ↓
   记忆闭环：错题 → 间隔复习 → 再评估
        ↓
   周复盘 / 重规划
```

- Phase 1 先跑通“规划 → 执行 → 看板”。
- Phase 2 补“提交 → 评审 → 评分趋势”。
- Phase 3 补“错题 → 复习”和“诊断 → 路线”。

### 2.2 与求职平台的分工

| 能力 | 求职平台 | 恒序 |
|---|---|---|
| 岗位/测评/题库/简历优化/AI 面试 | 提供 | 消费或回链 |
| 每日计划/执行跟踪 | 不做 | 核心 |
| 代码评审/错题复习 | 不做 | 核心（Phase 2/3） |
| 推送触达 | 不做 | 核心 |
| 社区/投递 | 提供 | 不做 |

当前只做入口链接，不做账号、简历、测评、错题、任务数据交换。

### 2.3 设计原则

1. **系统提议，用户确认**：AI 可以解析/评审/生成，但路线和计划的大改必须用户确认；锁定项不被覆盖。
2. **可完成优先于理论最优**：计划落在真实时间预算内；宁可少而完成，不可多而崩溃。
3. **一切任务可溯源**：任务能回答“属于哪个阶段/周、为什么今天做”。
4. **反馈必须具体**：评分要引用证据，给不超过 3 条可执行改进；拒绝“继续加油”。
5. **零整理**：用户每天只需确认、完成、跳过；不要求每天建任务。
6. **数据属于用户**：可导出、可删除、可关闭 AI 处理。

### 2.4 角色

- **用户**：管理自己的档案、路线、任务、练习、通知和授权。
- **系统/AI**：解析计划、生成建议、静态评审、生成复盘；写入动作保留来源和审计。
- **管理员（内部）**：Phase 1 不做管理后台；用脚本/DB/运维工具；多用户管理未来再评估。

## 3. 功能规格（按功能）

> 每个功能标注所属阶段。Phase 1 是当前开发范围；Phase 2/3 只锁定产品行为，详细技术设计见 [技术设计](02-技术设计.md)。

### 3.1 账户与档案

**目标**：让系统知道“你是谁、每天有多少时间、按哪个时区算今天”。

**规则**

- 注册/登录：邮箱或手机号 + 密码；JWT + Refresh Token。
- 档案：时区、每日可用分钟、计划容量系数（默认 0.8，允许 0.6–1.0）、日界线（默认 04:00）。
- 首次导入前必须同意“计划文本会发送给第三方 AI 解析”；记录授权 scope/version。
- 未配置推送不影响使用；设置页提示。

**页面**：登录、引导（档案 → 目标 → 导入 → 通知）、设置-档案。

**阶段**：Phase 1。

### 3.2 求职目标

**目标**：给路线一个明确的目标岗位和时间窗。

**规则**

- 字段：岗位、城市、行业、公司类型、目标日期、优先级。
- 同一时间只启用一个主目标；其他目标可归档。
- 目标变化后可重新生成/调整路线（Phase 3 AI 生成；Phase 1 手动/导入）。

**页面**：引导页、设置-目标。

**阶段**：Phase 1。

### 3.3 计划导入

**目标**：用户已经有一份计划（自己写的、其他 AI 生成的、Markdown 导出的），把它变成可执行任务。

**Phase 1 范围**：只支持 Markdown；HTML 放后续。

**流程**

```text
上传 .md
  → 规则抽取 + AI 标准化
  → 校验（字段/日期/容量/重复）
  → 预览（阶段/周/任务 + 问题清单）
  → 用户编辑
  → 确认
  → 创建路线/阶段/周/任务
  → 可回滚
```

**解析规则**

- `#/##/###` → 阶段/周/任务组。
- 无序列表、`- [ ]`、数字列表 → 任务。
- 表格列名匹配：任务、日期、时长、产出、验收、类型、优先级。
- 日期支持 `YYYY-MM-DD`、`MM/DD`、`第 N 天`、`第 N 周`。
- 无法识别的段落保留原文，交给 AI。

**任务必填**

- 标题、类型、预计时长、产出、验收标准。
- 日期可空；无日期按周/容量顺序分配，并标记为假设。
- 单任务 15–120 分钟；超过 120 分钟提示拆分。

**校验与处理**

- 总时长 ≤ 可用天数 × 有效日容量 × 0.8。
- 单日任务 ≤ 有效日容量。
- 重复任务（标题 + 日期）提示合并/跳过/保留。
- 开始日期早于今天：默认整体平移到今天；或保留历史并把过去任务归档。
- 缺失产出/验收：AI 给建议并标 warning，用户确认。
- 导入失败不影响已有路线；确认幂等；回滚仅限未产生执行记录的批次。

**页面**：导入上传、解析进度、预览树/日历、问题清单、内联编辑、确认/取消/重新解析。

**阶段**：Phase 1（Markdown）；HTML 后续。

### 3.4 路线、阶段、周、任务

**目标**：把计划变成可编辑、可追踪的层级结构。

**层级**

```text
路线 → 阶段 → 周目标 → 日任务
```

**任务字段**

- 标题、描述、学习目标、类型（算法/八股/工程/项目/简历/投递/复盘/面试）。
- 优先级、难度、预计时长、计划日期、截止日期。
- 产出要求、验收标准、推荐资料、能力标签（Phase 1 自由标签）。
- 是否可拆分、来源、状态。

**操作**

- 路线：创建、编辑、激活、暂停、恢复、归档、调整开始日期/日容量、查看版本。
- 阶段/周：增删改；有任务时删除返回 409。
- 任务：增删改、归档、批量调整。
- 删除语义：任务/路线是归档，不物理删除；历史 occurrence 不删除。

**状态**

- 路线：`draft → active → paused → active → completed/archived`。
- 任务模板：`draft/active/archived`。
- 每日执行状态在 `task_occurrences`，见 3.6。

**阶段**：Phase 1。

### 3.5 每日计划与今日页

**目标**：每天自动给出“今天做什么”，用户不用整理待办。

**输入池**

1. 已顺延的 occurrence。
2. 所属路线 active、任务 active、`planned_date ≤ today`、今天没有 occurrence 的任务。
3. 周期规则实例（Phase 1 预留，默认关闭）。
4. 用户手动添加的今日任务。

**容量**

```text
daily_capacity = floor(每日可用分钟 × 容量系数)
默认系数 0.8，允许 0.6–1.0
最低 30 分钟
```

**优先级**

```text
顺延任务 > 必做路线任务(P0) > 普通路线任务(P1/P2)
> 周期任务 > 可选任务
同优先级：截止日早 → 阶段顺序 → 优先级 → 预计时长短
```

**规则**

- 目标 3–6 项；先放顺延任务，再放路线任务，直到容量用尽。
- 顺延任务超过容量时全部放入并标 `over_capacity`，提示拆分/放弃，不静默丢弃。
- 单任务 >120 分钟优先拆分。
- 没有任务也创建空计划，便于推送/看板。
- 生成幂等：同一用户同一天只有一份 `daily_plan`；重复触发不重复创建。
- 生成时间：默认 06:00–08:00（用户时区）；打开今日页时可按需补生成。
- 今日页展示：日期、容量使用、完成率、任务卡（类型/阶段/来源/预计时长/为什么今天做）、顺延区、空状态。
- 任务操作：开始、完成（可填实际分钟/备注）、延期、跳过（原因）、阻塞（原因）、解除、放弃、拆分。

**阶段**：Phase 1。

### 3.6 任务执行与顺延

**执行状态**

```text
pending → in_progress → completed
pending/in_progress → postponed / skipped / blocked / abandoned
blocked → pending
```

完整迁移表与副作用见 [技术设计](02-技术设计.md) §3.3。

- `postponed`：旧实例终态，新实例进入下一天。
- `skipped`：写原因，任务 `planned_date` 置空，不再自动进入今日；可在路线详情重新排期。
- `blocked`：写原因；不自动变 pending，用户解除后恢复。
- `abandoned`：终态，任务归档，不计完成率。

**顺延**

- 日界线后，找旧日期 `pending/in_progress/blocked` 的实例。
- 计算剩余分钟：用户填写优先；否则 `max(计划 - 实际, 15)`。
- 创建今天的 occurrence：`carry_over_from_id`、`postpone_count+1`；blocked 保持 blocked 并复制原因。
- 旧实例标 `postponed`。
- 连续顺延 ≥3 次：提示拆分/降级/放弃。
- **容量回流，不硬移日期**：后续任务不改计划日期，由每日编排按容量重新选择；路线结束日期用剩余工作量预测。避免“一天没完成，整条计划雪崩”。

**阶段**：Phase 1。

### 3.7 进度看板

**目标**：让用户看到“计划执行得怎么样”，不是“能力有多强”。能力看板 Phase 3 再做。

**Phase 1 指标**

| 指标 | 定义 |
|---|---|
| 计划任务数 | 期间内 daily_plan_items 数 |
| 完成任务数 | status=completed 的 occurrence 数 |
| 任务完成率 | 完成任务数 / 计划任务数 |
| 计划分钟 / 实际分钟 | Σ planned_minutes / Σ actual_minutes |
| 时间偏差 | 实际分钟 / 计划分钟 |
| 顺延数/顺延率 | carry_over_from_id 非空 / 计划任务数 |
| 活跃天数 | 至少完成 1 项的天数 |
| 累计活跃天数 | 历史有完成记录的天数，不清零 |
| 路线进度 | 已完成任务数 / 路线总任务数（按 task 去重） |
| 预测完成日期 | 见技术设计 6.4 |
| 风险 | 预测日期 > 目标日期 |

技术计算口径见 [技术设计](02-技术设计.md) §6.5。

**口径**

- 完成率是 occurrence 口径；`abandoned` 不进分母；`skipped` 进分母但不计完成；`postponed` 计入原计划日、不计完成，新 occurrence 计入新计划日，所以跨天顺延会重复计入。
- 路线进度按 task 去重：一个任务有任一 completed 即算完成；archived/abandoned 不计入总数。
- 没有实际分钟时，完成任务的分钟按计划分钟估算并标注。
- 累计活跃天数不是连续打卡。

**页面**：总览卡、7/30 天趋势、时间/类型分布、路线进度、预测与风险、能力区（Phase 1 显示“完整能力评估后续开放”，不显示假分数）。

**阶段**：Phase 1；Phase 2 加代码评分趋势；Phase 3 加完整能力。

### 3.8 通知

**目标**：不用打开系统也知道今天做什么、做得怎么样。

**Phase 1 渠道**：企业微信群机器人（单向 Webhook）。

**事件**

| 事件 | 默认时间 | 触发 |
|---|---|---|
| 早报 | 07:30 | 今日计划已生成 |
| 晚报 | 20:30 | 今日有未完成任务 |
| 逾期 | 20:00 | 有逾期任务 |
| 顺延 | 日界线后 | 发生顺延 |
| 周总结 | 周日 20:00 | 本周有任务 |

技术实现、去重键、重试策略见 [技术设计](02-技术设计.md) §7。

**规则**

- 支持渠道配置、测试发送、模板、事件开关、发送时间、免打扰、失败重试、去重。
- 未配置渠道不发推送，今日页/看板仍可用。
- 群机器人不能收回复；消息里的操作通过链接回 Web，登录后操作。
- 免打扰：早报/晚报/周总结延迟到静默结束；逾期/顺延可丢弃。
- 消息必须带 `today_link`/`dashboard_link`；不发送无法操作的纯文本。

**阶段**：Phase 1。

### 3.9 代码练习与 AI 静态评审（Phase 2，方案 A）

**目标**：把每天算法题从“打个勾”变成“提交代码 → 得到带证据的评审 → 知道下一步改什么”。

**范围（方案 A）**

- 网页提交/粘贴代码。
- AI 只读代码和提交信息，**不执行代码、不做沙箱、不做 CLI/Git/IDE**。
- 正确性只给“静态风险 + 自测通过率”，不冒充 AC 判定。
- 不做代码运行、隐藏测试、性能实测。

评审输出 Schema、硬规则和 API 见 [技术设计](02-技术设计.md) §6.6。

**提交内容**

- 代码文件/粘贴文本。
- 语言。
- 题目来源/难度/标签。
- 自测结果（通过几组/失败用例；可填“未测”）。
- 自己判断的时间/空间复杂度。
- 是否独立完成。
- 可选：思路说明。

**评审维度**

| 维度 | 权重 | 看什么 |
|---|---|---|
| 正确性风险 | 35 | 边界、异常、约束、逻辑漏洞 |
| 复杂度 | 20 | 时间/空间分析与实现是否一致 |
| 代码质量 | 20 | 命名、结构、可读性 |
| 测试与验证 | 15 | 自测覆盖、断言 |
| 表达与复盘 | 10 | 思路说明、改进意识 |

**输出**

- 总分/等级/置信度。
- 维度分。
- 证据：文件/行号/代码片段/问题。
- 优点。
- ≤3 条改进：改哪里、怎么改、怎么验证。
- 1–3 个追问。
- 证据不足时标 `not_evaluated`，不编造。
- 正确性展示为“静态风险（低/中/高）+ 自测通过率”，不显示“AC/正确”。

**能/不能**

| 能做 | 不能做 |
|---|---|
| 发现逻辑漏洞、边界遗漏 | 证明一定 AC |
| 分析复杂度与实现是否一致 | 实测运行时间/内存 |
| 评价命名/结构/可读性 | 捕获所有运行时错误 |
| 指出测试覆盖不足 | 跑隐藏测试 |
| 检查思路与代码是否一致 | 替代判题 |

**页面**：今日算法任务卡增加“提交代码”；`/practice` 历史；`/practice/{id}` 提交/评审结果；评审结果包含分数、维度条、证据、改进、追问、重新提交。

**阶段**：Phase 2。

### 3.10 代码评分趋势（Phase 2）

**目标**：看“代码质量有没有变好”，不是“能力准备度”。

**指标**

- 最近 30 天平均分趋势。
- 提交次数、平均分、最高分。
- 维度趋势（正确性风险、复杂度、代码质量、测试、表达）。
- 自测通过率趋势（用户填写时）。
- 改进项完成率（下次提交是否改掉）。
- 最近 5 次提交。

**页面**：看板“算法评审”区块 + 练习历史。

**阶段**：Phase 2；不做能力准备度。

### 3.11 AI 诊断与路线生成（Phase 3）

**目标**：用户没有现成计划时，从简历、目标、困境生成可执行路线。

**输入**：简历、目标岗位、困境、每日时间、测评结果（可选）、历史执行。

**输出**：诊断（能力画像/差距/简历问题/项目表达问题/风险）、建议、阶段/周/日任务（含产出/验收）、路线草案。

**规则**

- 预览 → 用户调整（强度/周期/侧重/局部重生成）→ 确认 → 入计划。
- 不直接覆盖执行中的路线；保留版本。
- 总时长 ≤ 可用时长 × 0.8；每日 ≤ 容量；每周至少 1 个产出；每 7 天留缓冲/复盘日。
- 时间不够/目标过高要诚实提示，给替代方案。

**阶段**：Phase 3。

### 3.12 八股/项目每日提问（Phase 3）

**目标**：每天用 3–5 个问题检查“今天学的/以前学的/简历项目”是否真的会。

**题目来源**：今日任务、历史内容、错题、简历项目、目标岗位、低分能力项。

**题型**：基础、原理、代码、系统设计、项目追问、场景、反问/澄清。

**规则**

- 每日 3–5 题；支持文字作答、追问、限时。
- 评分维度：准确性、完整性、深度、结构表达、追问应对。
- 答错/低分自动生成错题。
- 不做语音（当前决策）。

**阶段**：Phase 3。

### 3.13 错题与间隔复习（Phase 3）

**目标**：错题不是记下来，而是按节奏复习到会。

**错题字段**：题目、来源、知识点、错误类型、原始答案、参考答案、AI 评价、首次错误、最近复习、下次复习、掌握程度、连续答对、复习历史。

**错误类型**：概念不清、记忆模糊、边界遗漏、复杂度错、表达结构缺失、细节记不清、审题错、完全不会。

**默认节奏**：学习后第 2 天 → 第 3 天 → 第 7 天 → 第 14 天 → 第 28 天。

实现为：

```json
{
  "first_review_after_days": 1,
  "intervals": [1, 4, 7, 14],
  "max_interval_days": 60,
  "reset_on_wrong": true
}
```

**自适应**

- 答对升一阶段；答错回退一阶段并次日重现。
- 答对但置信度低：重复当前阶段。
- 答对且置信度高：进入下一阶段。
- 超过最后阶段：倍率 + 上限，进入长期复习。
- 连续多次答对可归档；每月抽查。

**每日任务**

- 到期错题进入今日计划；默认每日最多 10 题或 35% 容量。
- 超期/积压只复习高优（lapses 高、关联本周重点、近期到期）。
- 复习完成回写掌握度、连续答对、下次复习。

**阶段**：Phase 3。

### 3.14 完整能力看板（Phase 3）

**目标**：把任务、代码、回答、错题证据汇总成“当前掌握度 / 目标达成度 / 准备度”。

**能力维度**：算法、数据结构、计算机网络、操作系统、数据库、语言基础、系统设计、工程化、项目表达、简历表达、面试沟通。

**规则**

- 每个目标岗位有 `job_capability_requirements`：target_level + weight。
- 证据来源权重：代码 1.0、工程 1.0、八股/项目 0.8、自评 0.3、外部测评 0.6。
- 时间衰减半衰期 30 天。
- 证据数 ≥3 且置信度 ≥0.5 才算 assessed；否则 unassessed。
- readiness 只在已评估能力上加权，并展示证据覆盖率；覆盖率 <50% 标低置信度。
- 没有证据显示“未评估”，不给 0 分。
- 趋势用日/周快照；预测偏差用 `route_forecast_history`。

**阶段**：Phase 3。

### 3.15 求职平台联动（Phase 3）

**目标**：从求职平台跳到恒序做每日跟踪，或从恒序跳回题库/面试官。

**规则**

- 只做固定 URL/页面路径入口。
- 不携带用户身份、简历、目标、测评、错题、任务状态。
- 不做 SSO、账号打通、数据同步、状态回传。
- 目标系统内独立登录和操作。

**阶段**：Phase 3。

### 3.16 设置、数据与管理

**设置**：时区、日界线、每日时间/容量、通知渠道/时间/免打扰、复习参数（Phase 3）、AI 授权。

**数据**：导出（后续）、删除账号（后续）、AI 解析授权记录。

**管理**：Phase 1 不做后台；管理员用脚本/DB/运维工具；多用户管理未来评估。

**阶段**：Phase 1 基础设置；数据/管理后续。

- 部分：任务部分完成、实际分钟未填、导入 warning。
- 权限：未登录、Token 过期。
- 时区：跨日、顺延、今日无计划。

## 5. 验收标准

### 5.1 Phase 1

1. 注册/登录，设置时区、每日可用时间、目标岗位。
2. 上传 Markdown，60 秒内完成解析（结构化样本），预览阶段/周/任务和问题。
3. 预览可编辑并重新校验；确认后生成路线/任务。
4. 手动新增/编辑/删除任务、阶段、周。
5. 今日计划 3–6 项、容量 ≤ 有效容量、重复触发不重复。
6. 今日页可开始/完成/延期/跳过/阻塞/解除/放弃/备注/填实际分钟。
7. 未完成自动顺延，次日出现，旧实例 postponed，预测日期更新。
8. 看板展示完成率、计划/实际分钟、趋势、分布、顺延率、路线进度、预测，数字与数据库一致。
9. 企微 Webhook 可配置/测试；早报/晚报/逾期/顺延/周总结按时间发送。
10. 通知失败可重试，dead 可见并手动重发；同一消息不重复。
11. 导入失败不影响已有路线；回滚可用。
12. 所有接口按用户隔离；越权返回 404/403；Webhook SSRF 被拦截。
13. E2E 跑通；关键操作有审计日志。
14. 手机/桌面可用；空态/加载/错误态完整。
15. 首次导入前取得 `ai_import` 同意；未同意只能手动创建。

### 5.2 Phase 2（方案 A）

1. 算法任务可提交代码 + 语言/题目/难度/自测/复杂度/独立性/思路。
2. 60 秒内返回结构化评审：总分、维度、证据、优点、≤3 改进、追问、置信度。
3. 每条问题有文件/行号证据；无证据标 `not_evaluated`。
4. 正确性显示为“静态风险 + 自测通过率”，不显示 AC/正确。
5. 评审结果可查看/重新提交/对比。
6. 看板显示评分趋势、提交次数、平均分、维度趋势。
7. 没有沙箱、没有代码执行、没有 CLI/Git/IDE。
8. 用户可标记改进项完成；趋势能反映。

### 5.3 Phase 3

- 诊断/路线可生成、预览、调整、确认、版本化。
- 每日提问 3–5 题，支持追问和错题生成。
- 错题按第 2/3/7/14/28 天节奏进入今日任务，可配置、可积压处理。
- 能力看板按证据计算，未评估不造假。
- 平台入口只跳转、不传数据。

### 7.2 指标口径

- 完成率 = 完成 occurrence / 计划 occurrence；abandoned 不进分母；skipped 进分母不计完成；postponed 计入原计划日、新 occurrence 计入新计划日。
- 路线进度 = 完成任务数 / 总任务数（按 task 去重）。
- 代码评分趋势 = 评审总分的时间序列；不是能力分。
- 能力 readiness = 已评估能力加权；覆盖率单独展示。

### 7.3 Markdown 模板

```markdown
# 30 天后端冲刺

- 开始：2026-10-20
- 结束：2026-11-18
- 每日可用：120 分钟

## 阶段一：基础夯实（10/20 - 11/02）

### 第 1 周：网络基础

- [ ] TCP 三次握手（45 分钟）
  - 产出：口述录音/笔记
  - 验收：不看资料讲清状态机
- [ ] HTTP 缓存（45 分钟）
  - 产出：思维导图
  - 验收：能区分强缓存/协商缓存
```
