## 1. 接入准备

### 1.1 地址

| 项 | 本地值 |
|---|---|
| API Base URL | `http://127.0.0.1:8000` |
| API 前缀 | `/api/v1` |
| Swagger | `http://127.0.0.1:8000/docs` |
| OpenAPI | `http://127.0.0.1:8000/openapi.json` |
| 前端开发地址 | `http://localhost:3000`（默认 CORS 允许） |

### 1.2 推荐部署方式：同源反向代理

推荐用 Next.js rewrite / Nginx 把 `/api/*` 反代到后端，浏览器只看到前端自己的域名：

```text
浏览器 → https://app.example.com
          ├── /            → Next.js 前端
          └── /api/*       → FastAPI
```

这样 Cookie 与 CORS 最简单。若前后端不同源，必须同时满足：

1. 后端 `CORS_ORIGINS` 包含前端完整 Origin（协议 + host + port）。
2. 前端请求带 `credentials: "include"`（fetch）或 `withCredentials: true`（axios）。
3. 浏览器访问前端和 API 使用**同一个 host**（不要一个用 `localhost`、一个用 `127.0.0.1`，否则 Cookie 的 SameSite 会拦截）。

相关配置：

```text
# 本地默认已包含 localhost/127.0.0.1 的 3000 和 3001
CORS_ORIGINS=http://localhost:3000,http://localhost:3001,https://app.example.com
REFRESH_COOKIE_SECURE=true   # 生产 HTTPS；本地 HTTP 开发留空/默认 false
```

### 1.3 生成 TypeScript 客户端

```powershell
.\.venv\Scripts\python.exe scripts\export_openapi.py
# 然后使用 openapi-typescript / orval / openapi-generator 生成
npx openapi-typescript docs/openapi.json -o src/api/schema.d.ts
```

不要手写接口类型；契约变更后重新生成并跑类型检查。

## 2. 认证与会话

### 2.1 Token 模型

| Token | 存放 | 有效期 | 前端可读 | 说明 |
|---|---|---|---|---|
| Access Token | 响应体，前端内存 | 30 分钟 | 是 | 放 `Authorization: Bearer`，**不要写 localStorage** |
| Refresh Token | `HttpOnly` Cookie | 30 天 | **否** | 只由浏览器自动发送；JS 读不到，也不要尝试读 `document.cookie` |

Cookie 属性：

```text
Name: persistlog_refresh
Path: /api/v1/auth
HttpOnly: true
SameSite: Lax
Secure: 生产 true，本地 HTTP false
Max-Age: 2592000（30 天）
```

### 2.2 登录/注册

```http
POST /api/v1/auth/register
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "password123",
  "display_name": "清瞳",
  "timezone": "Asia/Shanghai"
}
```

```http
HTTP/1.1 201 Created
Set-Cookie: persistlog_refresh=...; HttpOnly; Path=/api/v1/auth; SameSite=lax; Max-Age=2592000

{
  "access_token": "eyJ...",
  "token_type": "bearer",
  "expires_in": 1800,
  "user": {
    "id": "...",
    "email": "user@example.com",
    "display_name": "清瞳",
    "timezone": "Asia/Shanghai",
    "status": "active",
    "created_at": "2026-10-20T01:23:45"
  }
}
```

登录：`POST /api/v1/auth/login`，body `{email, password}`，响应同上（200）。密码长度 8–128。

> **重要**：响应体**不再包含 `refresh_token`**。前端只需保存 `access_token`；刷新由浏览器 Cookie 自动完成。

### 2.3 刷新与 401 重试

```http
POST /api/v1/auth/refresh
# 浏览器不需要 body；Cookie 自动携带
```

响应 200：新的 `access_token`，并轮换 Cookie（旧 Refresh Token 立即失效）。

推荐的前端逻辑：

```ts
async function request(path: string, init: RequestInit = {}) {
  let response = await fetch(path, {
    ...init,
    credentials: "include",
    headers: {
      ...init.headers,
      Authorization: `Bearer ${accessToken}`,
    },
  });

  if (response.status === 401) {
    // 单飞：同一时间只允许一个 refresh 请求
    const refreshed = await refreshOnce();
    if (!refreshed) {
      clearSessionAndRedirectToLogin();
      return response;
    }
    response = await fetch(path, {
      ...init,
      credentials: "include",
      headers: {
        ...init.headers,
        Authorization: `Bearer ${accessToken}`,
      },
    });
  }
  return response;
}
```

规则：

1. 只有 `401` 才尝试刷新；`403` 不要刷新（可能是 CSRF/越权）。
2. 刷新失败（401 `INVALID_REFRESH_TOKEN`）→ 清空内存 token，跳登录。
3. 刷新请求必须单飞，避免并发 401 触发多次轮换，导致旧 token 被判重放。
4. 刷新成功后原请求**最多重试一次**。
5. `POST /auth/refresh`、`POST /auth/logout` 不要手写 `refresh_token` body，浏览器用 Cookie 即可。

### 2.4 登出

```http
POST /api/v1/auth/logout
# 浏览器 Cookie 自动携带
```

`204 No Content`，响应会 `Set-Cookie` 清空 Refresh Cookie。前端同时清空内存 access token 和用户状态。

### 2.5 CSRF / Origin

- `/auth/refresh`、`/auth/logout` 会校验请求的 `Origin` 是否在 `CORS_ORIGINS` 中。
- 浏览器会自动带 `Origin`；**不要让代理或网关删掉它**。
- 非允许来源返回 `403 CSRF_ORIGIN_REJECTED`。

### 2.6 认证常见错误

| HTTP | code | 场景 |
|---|---|---|
| 401 | `UNAUTHORIZED` | 没带 Bearer / Bearer 无效 |
| 401 | `TOKEN_EXPIRED` | Access Token 过期 |
| 401 | `INVALID_TOKEN` | Access Token 非法 |
| 401 | `INVALID_CREDENTIALS` | 邮箱或密码错误 |
| 401 | `INVALID_REFRESH_TOKEN` | Refresh 过期、已撤销或重放 |
| 403 | `CSRF_ORIGIN_REJECTED` | Origin 不在白名单 |
| 409 | `EMAIL_ALREADY_EXISTS` | 邮箱已注册 |
| 429 | `RATE_LIMITED` | 登录超过 5 次/分钟/IP |

## 3. 通用约定

### 3.1 请求与响应

- JSON UTF-8；`Content-Type: application/json`。
- 日期字段：`YYYY-MM-DD`。
- 时间戳：UTC，但当前序列化为**不带时区后缀**的 ISO 字符串（例如 `2026-10-20T01:23:45`）。
  - 前端解析时统一按 UTC 处理（可追加 `Z` 再 `new Date()`），或只展示日期。
  - 这是当前实现限制，后续会在序列化层补 `Z`/offset。
- 用户时区、日界线（默认 04:00）由后端计算；前端不要自己用浏览器时区推“今天”。
- 每个响应带 `X-Request-ID`；报错时把它显示在错误提示/日志里，便于后端排查。

### 3.2 错误包

```json
{
  "error": {
    "code": "IMPORT_VALIDATION_FAILED",
    "message": "导入计划存在 3 个错误",
    "details": { "issues": 3 },
    "request_id": "9f0c..."
  }
}
```

常见错误码：

| HTTP | code | 说明 |
|---|---|---|
| 401 | `UNAUTHORIZED` / `TOKEN_EXPIRED` / `INVALID_TOKEN` | 未登录/登录过期 |
| 401 | `INVALID_CREDENTIALS` / `INVALID_REFRESH_TOKEN` | 登录失败/刷新失败 |
| 403 | `CSRF_ORIGIN_REJECTED` | 来源不被允许 |
| 404 | `NOT_FOUND` / `IMPORT_NOT_FOUND` / `ROUTE_NOT_FOUND` / `TASK_NOT_FOUND` / `OCCURRENCE_NOT_FOUND` | 资源不存在或不属于当前用户 |
| 409 | `IMPORT_INVALID_STATE` / `OCCURRENCE_INVALID_STATE` / `ROUTE_INVALID_STATE` / `TODAY_ITEM_INVALID` | 当前状态不允许该操作 |
| 409 | `STAGE_HAS_TASKS` / `WEEK_HAS_TASKS` / `TASK_HAS_OCCURRENCES` | 有下级数据，不能删除 |
| 409 | `STAGE_ORDER_CONFLICT` / `WEEK_NO_CONFLICT` | 序号冲突 |
| 413 | `FILE_TOO_LARGE` | 文件超过 5MB |
| 422 | `VALIDATION_ERROR` | 请求字段校验失败 |
| 422 | `UNSUPPORTED_FILE_TYPE` / `EMPTY_FILE` / `INVALID_FILE_ENCODING` | 文件类型/空文件/非 UTF-8 |
| 422 | `IMPORT_VALIDATION_FAILED` | 导入校验有 error，不能确认 |
| 422 | `TASK_WEEK_REQUIRED` / `TASK_REF_MISMATCH` / `TASK_DATE_OUT_OF_RANGE` / `INVALID_TASK_TYPE` | 任务层级/日期/类型不合法 |
| 422 | `INVALID_ROUTE_DATES` / `INVALID_TIMEZONE` | 路线日期或时区不合法 |
| 422 | `NOTIFICATION_CHANNEL_INVALID` / `NOTIFICATION_PREFERENCE_INVALID` | 企微配置或偏好不合法 |
| 429 | `RATE_LIMITED` | `details.retry_after` 为建议等待秒数 |
| 500 | `INTERNAL_ERROR` / `IMPORT_FAILED` | 服务端错误 |
| 502 | `NOTIFICATION_SEND_FAILED` | 通知发送失败 |
| 502 | `AI_PROVIDER_ERROR` | AI 服务失败；导入会自动降级为规则解析并返回 warning |

### 3.3 分页与幂等（当前限制）

- **没有实现 `page/page_size` 分页**。`GET /imports`、`/routes`、`/tasks`、`/job-targets`、`/notification-channels` 等返回完整数组。
- 只有 `GET /notification-outbox?limit=`、`GET /audit-logs?limit=` 有 `limit`（1–200，默认 50）。
- **没有实现 `Idempotency-Key`**；不要依赖它做重复提交保护。
- 数据量变大前，前端先按全量列表处理；后端补分页时以兼容方式新增。

### 3.4 限流

| 操作 | 限制 |
|---|---|
| 登录 | 5 次/分钟/IP |
| 创建导入 | 3 次/小时/用户 |
| 通知测试发送 | 5 次/小时/用户 |

### 3.5 枚举

**task_type**：`algorithm`、`fundamentals`、`engineering`、`project`、`resume`、`apply`、`review`、`interview`、`reflection`。

**priority**：`P0`、`P1`、`P2`。

**route.status**：`draft`、`active`、`paused`、`completed`、`archived`。

**task.status**：`draft`、`active`、`archived`。

**occurrence.status**：`pending`、`in_progress`、`completed`、`postponed`、`skipped`、`blocked`、`abandoned`；`pending_review/reviewed` 为 Phase 3 预留，Phase 1 不会出现。

**import.status**：`parsing`、`needs_review`、`confirmed`、`failed`、`cancelled`、`rolled_back`（DDL 还包含 `uploaded`，当前创建后直接进入 `parsing`）。

**job.status**：`queued`、`running`、`succeeded`、`failed`、`cancelled`。

**notification.status**：`pending`、`sending`、`sent`、`failed`、`dead`。

## 5. 关键流程

### 5.1 首次引导

```text
注册/登录
  → GET /profile（读取默认档案）
  → PUT /profile（时区、每日可用分钟、容量系数、日界线）
  → POST /job-targets（目标岗位；可设 is_primary）
  → GET /consents，然后 PUT /consents（ai_import 同意）
  → POST /imports（上传 Markdown）
  → GET /jobs/{id} 轮询
  → GET /imports/{id}/preview
  → PATCH /imports/{id}/preview（可选编辑）
  → POST /imports/{id}/confirm
  → GET /today
  → POST /notification-channels + /test（可选）
```

### 5.2 导入流程与状态

```text
POST /imports
  → 201 {import_id, job_id, status}
  → 轮询 GET /jobs/{job_id}
      status: queued → running → succeeded/failed
      progress: 0.05 → 0.15 → 0.40 → 0.65 → 0.85 → 1.00
  → job.status=succeeded 时：
      batch.status=needs_review（可预览/编辑/确认）
      或 batch.status=failed（看 issues，修正后 PATCH preview 再确认）
  → job.status=failed 时：
      看 job.error.code/message；批次也可能已标记 failed
```

前端处理建议：

- `POST /imports` 返回后立即开始轮询，间隔 1 秒，最多 60 秒；超时提示“仍在处理，可稍后在导入列表查看”。
- 如果 `created.status` 已经是 `needs_review`（Broker 不可用时的同步降级），直接进入预览，不要死等 Job。
- 预览页展示 `stats`（stages/weeks/tasks/total_minutes）、`assumptions`、`warnings`、`issues`。
- `issues[].severity` 为 `error` 时不能确认；`warning` 可确认但需提示。
- `PATCH preview` 必须提交**完整 route 对象**（前端在预览树上整体编辑后提交）；响应带 `updated_at`，可用于判断是否已持久化。
- **确认使用后端当前 preview**：只改前端本地状态、不调用 PATCH，`confirm` 仍会用原始 preview。前端编辑后必须先 PATCH 成功，再允许确认。
- 确认幂等：重复调用返回同一 `route_id`；回滚只允许未产生执行记录的路线。

操作与状态：

| 操作 | 允许的当前状态 | 结果 |
|---|---|---|
| `start` | `pending`；`in_progress` 重复调用幂等 | `in_progress` |
| `complete` | `pending` / `in_progress` | `completed`，写 `completed_at`、`actual_minutes`（默认计划分钟） |
| `postpone` | `pending` / `in_progress` | 旧实例 `postponed`；次日创建 `pending` 新实例，`postpone_count+1` |
| `skip` | `pending` / `in_progress` | `skipped`，写原因；任务 `planned_date` 置空 |
| `block` | `pending` / `in_progress` | `blocked`，写原因 |
| `unblock` | `blocked` | `pending` |
| `abandon` | `pending` / `in_progress` / `blocked` | `abandoned`，任务归档 |
| `split` | `pending` / `in_progress` | 生成 2–4 个子实例，返回数组 |

前端建议：

- 操作用乐观更新，失败用返回的错误包回滚并提示。
- 操作成功后失效 `today`、`dashboard`、`routes` 相关 query。
- `carry_over` 与 `items` 都展示；`carry_over=true` 或 `carry_over_from_id` 非空表示顺延任务。
- 连续顺延 ≥3 次时提示拆分/降级/放弃（后端已写 `postpone_count`）。
- `GET /today` 首次访问会触发计划生成；如果响应慢，展示骨架屏，不要重复并发调用。
- **已有空计划会自动补齐**：先访问过 `/today`、后导入路线，也会在下次 `GET /today` / `POST /today/generate` 时补入当天到期的路线任务；不需要删计划。
- **手动加任务**：`POST /today/items` 传 `task_id` 或新建 `title`，返回完整 `TodayResponse`；前端直接替换当天数据，不要只加内存。临时任务 `source_type=manual`、不挂路线，不计入路线进度；要计入路线请用 `task_id` 加已有任务。
- 历史日期查看传 `?date=YYYY-MM-DD`。

## 8. 前端工程建议

- **框架**：Next.js App Router + TypeScript + Ant Design + TanStack Query。
- **API 客户端**：由 `openapi.json` 生成类型；不要手写重复类型。
- **状态**：服务端状态用 TanStack Query；access token 放内存/Context；不要进 localStorage。
- **401**：统一拦截、单飞刷新、失败跳登录；见 2.3。
- **日期**：统一用 `YYYY-MM-DD` 字符串；不要把 `new Date()` 的本地时区结果直接传给后端。
- **时间戳**：按 UTC 解析（当前无后缀，追加 `Z`）。
- **错误**：统一读取 `error.code/message/details/request_id`；按 code 做具体提示，不要只弹“请求失败”。
- **空/加载/错误态**：每个页面都要覆盖；导入和今日页尤其需要骨架屏。
- **移动端**：今日页优先适配 375px；任务卡操作按钮不要溢出。
- **权限**：所有请求带 Bearer；不要传 `user_id` 过滤（后端强制当前用户）。
- **无障碍**：按钮有可读文本；状态不要只靠颜色区分。

## 9. 已知限制与联调注意事项

1. **没有分页**：列表接口返回全量数组；数据量大时先在前端做虚拟滚动/折叠。
2. **没有 `Idempotency-Key`**：重复提交由前端按钮防抖 + 后端唯一约束/状态机兜底。
3. **AI 导入授权未强制**：后端只记录 `ai_import`，不拦截未授权导入；前端必须在首次导入前调用 `PUT /consents`。
4. **真实 AI 已接但质量待评估**：当前 DeepSeek `deepseek-flash` 已跑通真实导入；样本量小，前端不要把“AI 拆解”描述成确定能力。Provider 失败会自动降级规则解析，预览会返回 warning。
5. **真实企微已验证**：测试/早报/晚报/逾期/顺延/周总结已真实发送；Webhook 只存密文，接口只返回 masked。更换机器人后需在设置页重新配置。
6. **Redis 登录自启，Worker/Beat 需手动启动**：Redis 已配置计划任务 `persistLog-Redis`（用户登录时启动，注销后可能停止）；登录后仍需运行 `scripts/start_worker.ps1`、`start_beat.ps1`。Worker 不在时导入会降级同步，通知不会自动发送。
7. **`send_time` 未动态调度**：偏好字段可存，但 beat 用固定时间。
8. **导入可能同步完成**：Redis 不可用时 `POST /imports` 返回时批次已是 `needs_review`；前端要同时兼容“立即完成”和“轮询”。
9. **Cookie 跨域限制**：不同 host 的 `localhost` / `127.0.0.1` 会被 SameSite 拦截；推荐同源反代。
10. **OpenAPI 只声明 HTTPBearer**：Refresh Cookie 不在 securitySchemes 里，以本文 2.1/2.2 为准。
11. **旧 `storage/` 目录权限异常**：本地起 API 时设置 `STORAGE_DIR=storage_dev` 或其它可写目录。
12. **无文件预签名**：导入直接 multipart 上传，不要调用 `/files/presign`（未实现）。
13. **时间戳无时区后缀**：按 UTC 解析，等后端补 `Z` 后再简化。
14. **Phase 2/3 页面未实现**：`/practice`、`/quiz`、`/mistakes` 等路由先不要做。
