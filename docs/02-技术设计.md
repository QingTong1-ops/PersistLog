## 0. 范围与原则

### 0.1 当前范围

- **Phase 1（当前开发）**：计划导入、路线/任务、每日计划、今日页、顺延、执行看板、企微推送。
- **Phase 2（下一步）**：网页提交代码 + AI 静态评审 + 评分趋势；**方案 A：不执行代码、无沙箱、无 CLI/Git/IDE**。
- **Phase 3（后续）**：AI 诊断/路线、八股/项目提问、错题复习、完整能力看板、平台入口。
- **不在当前路线**：沙箱判题、CLI/IDE、平台数据交换、语音、社区、招聘投递、管理后台。

### 0.2 架构原则

1. 模块化单体优先，保留拆服务边界。
2. 同步请求与异步任务分离。
3. 先落库，再调用 AI；AI 失败不丢用户输入。
4. AI 输出必须结构化、可校验、可追溯；不能直接写库。
5. 所有业务数据按 `user_id` 隔离。
6. 日执行状态只认 `task_occurrences`。
7. Phase 1 不引入 LangGraph；Phase 2/3 需要多步人工确认时再引入。
8. 通知只做单向推送；企微群机器人不能收回复。
9. 所有异步任务统一 Job 契约。
10. 时间为用户时区；数据库存 UTC，日期按用户时区计算。

### 1.3 同步与异步

**同步**

- 登录/刷新、档案/目标 CRUD。
- 路线/阶段/周/任务 CRUD。
- 今日查询、任务状态变更。
- 看板查询。

- Markdown 解析 + AI 标准化 + 校验。

### 1.4 AI 编排边界

- **Phase 1**：导入是一条 Celery 流水线 + 一次结构化 AI 调用；不引入 LangGraph。
- **Phase 2**：代码评审是“组装上下文 → 一次结构化评审 → 校验 → 落库”；仍不需要 LangGraph。
- **Phase 3**：诊断/路线生成、每日提问、复盘涉及多步人工确认和暂停恢复时，再引入 LangGraph StateGraph；核心业务数据仍由领域服务/ MySQL 管理。
- **AI Gateway**：统一 provider/model、超时、重试、限流、结构化输出校验、Token/成本、Prompt 版本、审计。

## 3. 领域模型与状态机

### 3.1 核心对象

| 对象 | 职责 |
|---|---|
| User | 账号、时区、状态 |
| UserProfile | 每日可用时间、容量系数、日界线 |
| UserConsent | AI 解析/隐私授权 |
| JobTarget | 目标岗位、目标日期、优先级 |
| Route | 学习路线 |
| RouteVersion | 路线快照 |
| Stage / Week | 阶段/周目标 |
| Task | 任务模板 |
| DailyPlan / DailyPlanItem | 某天计划快照 |
| TaskOccurrence | 某天执行实例 |
| ImportBatch/Item/Issue | 导入批次/项/问题 |
| NotificationChannel/Template/Preference/Outbox | 通知 |
| File / Job / AiRun / AuditLog | 文件/异步/AI/审计 |

### 3.2 任务模板 vs 执行实例

- `tasks`：任务模板，状态 `draft/active/archived`；存标题、类型、估时、产出、验收、能力标签、计划日期。
- `task_occurrences`：某天实际执行实例；存状态、计划/实际/剩余分钟、顺延来源、跳过/阻塞原因、备注、拆分。
- **今日列表、完成率、顺延、看板全部以 occurrence 为准。**
- 一个任务同一天可有多个拆分实例，唯一键 `(user_id, task_id, occurrence_date, split_index)`。

### 3.3 执行状态机

```text
pending → in_progress → completed
（Phase 3：completed → pending_review → reviewed）
pending/in_progress → postponed / skipped / blocked / abandoned
blocked → pending
```

| 当前 | 动作 | 下一状态 | 副作用 |
|---|---|---|---|
| pending | start | in_progress | 写 started_at |
| in_progress | complete | completed | 写 completed_at、actual_minutes |
| completed | review（Phase 3） | pending_review/reviewed | Phase 3 使用 |
| pending/in_progress | postpone | postponed | 创建次日 occurrence，写 carry_over_from_id |
| pending/in_progress | skip | skipped | 写原因；任务 planned_date 置空 |
| pending/in_progress | block | blocked | 写原因 |
| blocked | unblock | pending | 清除原因 |
| pending/in_progress/blocked | abandon | abandoned | 终态；任务归档；不计完成率 |
| pending/in_progress | split | 子 occurrence | 写 parent/split_index |

规则：

- `postponed` 是旧实例终态；新实例才是下一天可执行项。
- Phase 1 完成任务停在 `completed`；`pending_review/reviewed` 仅预留。
- `abandoned` 不从完成率分母扣除任务本身，而是排除该 occurrence；任务归档。

### 3.4 路线状态机

```text
draft → active → paused → active
active → completed
active/paused/completed → archived
```

- 一个求职目标同一时间只允许一条 active 路线。
- 导入确认后默认 active；开始日期在未来也可以 active。
- 所有 active 任务完成且无未完成 occurrence 时提示“路线已完成”；Phase 1 由用户手动完成/归档。

### 3.5 导入状态机

```text
uploaded → parsing → needs_review → confirmed
                    ↘ failed
confirmed → rolled_back
uploaded/parsing/needs_review → cancelled
```

- 只有未产生执行记录的批次可回滚。
- 确认幂等：重复确认返回已创建路线。
- 失败保留原文，允许重试/手动创建。

### 3.6 通知状态机

```text
pending → sending → sent
                 ↘ failed → pending（重试）
                          ↘ dead
```

- 唯一键 `(user_id, dedup_key)`。
- 重试 1/5/30 分钟，最多 3 次；dead 可手动重发。

### 3.7 不变量

1. 所有业务表必须有 `user_id`；查询必须带 `user_id`。
2. `daily_plans(user_id, plan_date)` 唯一。
3. `task_occurrences(user_id, task_id, occurrence_date, split_index)` 唯一。
4. 一个 job_target 同时只有一条 active 路线。
5. 路线开始 ≤ 结束；任务计划日期在路线范围内。
6. 任务必须有标题、类型、预计时长、产出、验收。
7. 导入确认幂等；通知 dedup 幂等。
8. 归档路线/任务不影响已完成 occurrence 和历史统计。

## 5. API 契约

### 5.1 通用约定

- Base path：`/api/v1`。
- 认证：Access Token 放 `Authorization: Bearer <access_token>`；Refresh Token 只放 `HttpOnly` Cookie，前端不写 localStorage。
- CORS：只允许 `CORS_ORIGINS` 白名单来源，`allow_credentials=true`；Cookie 认证的写操作额外校验 `Origin`。
- JSON，UTF-8；日期 `YYYY-MM-DD`；时间 ISO 8601 UTC。
- 分页：`page/page_size`，响应 `items/total/page/page_size`。
- 幂等：POST 支持 `Idempotency-Key`，保存 24 小时。
- 异步：导入返回 `201 {import_id, job_id, status}`，用 `GET /jobs/{id}` 轮询；Job 状态 `queued/running/succeeded/failed`。
- 错误：

```json
{
  "error": {
    "code": "IMPORT_VALIDATION_FAILED",
    "message": "导入计划存在 3 个错误",
    "details": { "issues": 3 },
    "request_id": "..."
  }
}
```

- 权限：所有业务查询强制当前用户；Phase 1 只有 `user` 角色。
- 限流：登录 5 次/分钟/IP；导入 3 次/小时/用户；通知测试 5 次/小时/用户。

## 6. 核心算法

### 6.1 计划导入

**流水线**

```text
文件校验 → 文本抽取 → 规则解析 → AI 标准化 → Schema/业务校验
→ 预览/问题清单 → 用户编辑 → 确认落库 → 可回滚
```

**执行方式**

- 创建导入时先落库 `import_batches` + `jobs`，再入队 Celery `process_import` 任务；Worker 内执行同一流水线并更新 `progress`。
- Broker 不可用时降级为请求内执行，保证本地无 Worker 也能完成导入。
- 前端用 `GET /jobs/{id}` 轮询；`result_ref = import:{batch_id}`，失败时 `error` 返回 `code/message`。
- 批次进入 `needs_review/failed/confirmed/cancelled/rolled_back` 后任务幂等跳过。

**规则解析**

- 标题层级 → 阶段/周/任务组。
- 列表/checkbox → 任务。
- 表格列名匹配字段。
- 日期格式：`YYYY-MM-DD`、`MM/DD`、`第 N 天`、`第 N 周`。
- 无法识别段落保留原文交 AI。

**AI 输出 Schema**

```json
{
  "route": {
    "title": "string",
    "start_date": "YYYY-MM-DD",
    "end_date": "YYYY-MM-DD",
    "stages": [
      {
        "name": "string",
        "objective": "string",
        "weeks": [
          {
            "week_no": 1,
            "focus": "string",
            "milestone": "string",
            "tasks": [
              {
                "title": "string",
                "task_type": "algorithm|fundamentals|engineering|project|resume|apply|review|interview|reflection",
                "planned_date": "YYYY-MM-DD|null",
                "estimated_minutes": 45,
                "learning_objective": "string",
                "description": "string",
                "deliverable": "string",
                "acceptance_criteria": "string",
                "priority": "P0|P1|P2",
                "resources": ["string"],
                "capability_tags": ["string"],
                "source_locator": "line 12",
                "assumptions": ["string"]
              }
            ]
          }
        ]
      }
    ]
  },
  "assumptions": ["string"],
  "warnings": ["string"]
}
```

**校验**

- 必填：title/task_type/estimated_minutes/deliverable/acceptance。
- 日期在路线范围内；无日期按周/容量分配并标 assumption。
- 总时长 ≤ 天数 × 有效容量 × 0.8；单日 ≤ 有效容量。
- 单任务 15–120 分钟；超长提示拆分。
- 重复任务 warning；未知能力标签 warning。
- 开始日期早于今天：默认平移到今天，或保留历史并归档过去任务。

**AI 约束**

- 不发送计划文本以外的用户数据。
- 计划文本按不可信数据处理；分隔符 + 明确指令防 Prompt Injection。
- 输出必须过 JSON Schema；失败修复一次；仍失败降级为手动。
- AI 不得直接写库；只能生成预览。
- 记录 `ai_runs`：provider/model/prompt_version/input_hash/output/token/latency。

**Provider 实现**

- `AI_PROVIDER=stub`：本地确定性解析，测试默认。
- `AI_PROVIDER=deepseek` / `openai_compatible`：调用 `{AI_BASE_URL}/chat/completions`，`response_format=json_object`，当前本地使用 `deepseek-flash`。
- Provider 异常时回退规则解析，批次仍进入 `needs_review`，预览带 `warnings`，`ai_runs.status=failed` 记录原因。
- 原始计划按不可信数据放入 `<PLAN>` 分隔区；提示词明确禁止执行计划内指令。

### 6.2 每日计划生成

**触发**

- 设计目标：Celery Beat 每 15 分钟扫描，按用户时区在 06:00–08:00 生成。
- 当前实现：打开 `/today` 时按需 `ensure_today`；通知任务也会调用 `ensure_today`。**06:00–08:00 的独立 beat 生成任务尚未实现**。
- 生成幂等。

**输入池**

1. 已顺延 occurrence。
2. 路线 active、任务 active、`planned_date ≤ today`、今天无 occurrence。
3. 周期规则（Phase 1 预留）。
4. 用户手动今日任务。

**排除**

- 今天已有 occurrence 的任务。
- archived 任务；skip 后 planned_date 置空；abandon 归档。

**容量**

```text
daily_capacity = floor(daily_available_minutes × planning_capacity_factor)
默认 0.8，允许 0.6–1.0；最低 30 分钟
```

**优先级**

```text
顺延 > P0 路线任务 > P1/P2 路线任务 > 周期 > 可选
同优先级：due_date 早 → stage.order_no 小 → priority 高 → 预计时长短
```

**选择**

- 顺延任务全部放入；超容量标 `over_capacity`，提示拆分/放弃。
- 路线任务填满容量或达到 6 项。
- 预留 10% 给临时任务；不足可超 10% 但提示。
- 单任务 >120 分钟优先拆分。
- 无任务也创建空计划。
- **已有计划补齐**：先访问 `/today` 生成空计划、后导入路线时，下次 `GET /today` / `POST /today/generate` 会补入当天到期任务；保留原 plan_id，不删除已完成项。
- **手动加入**：`POST /today/items` 支持 `task_id`（已有任务）或 `title`（临时任务）；写入 `tasks` + `task_occurrences` + `daily_plan_items`，并更新 `summary_json`。

**幂等**

- `daily_plans(user_id, plan_date)` 唯一。
- `task_occurrences(user_id, task_id, occurrence_date, split_index)` 唯一。
- 重复生成返回已有计划；只补缺失项，不删已完成。
- 手动加入同一 `task_id` 重复调用不会产生第二条 occurrence。

**解释**

`summary_json` 保存 focus/capacity/planned/selected/deferred。

### 6.3 未完成顺延

**触发**：日界线后或生成次日计划前。

**步骤**

1. 找旧日期 `pending/in_progress/blocked` 实例。
2. 计算剩余：用户填写优先；否则 `max(planned - actual, 15)`。
3. 创建今天 occurrence；`pending/in_progress` → pending，`blocked` 保持 blocked 并复制原因；写 carry_over_from_id；postpone_count+1。
4. 旧实例标 `postponed`。
5. postpone_count ≥3 提示拆分/降级/放弃。
6. 更新预测日期。

**容量回流**：后续任务不改 planned_date；每日编排按容量重选；避免整条路线逐日平移。

**通知**：顺延几项、预测日期变化、今日重点。

### 6.4 预测完成日期

```text
remaining = Σ occurrence.remaining_minutes（未完成/未跳过/未放弃）
          + Σ task.estimated_minutes（未生成 occurrence 的 active 任务）

throughput = 最近 14 天有记录日的 median(actual_minutes)，>=5 天
           else daily_capacity
throughput = max(throughput, 30)

forecast_days = ceil(remaining / throughput × 1.1)
forecast_end_date = today + forecast_days
```

- 预测 > 路线结束/目标日期 → 看板 risk=behind。
- 每次完成/顺延/调整后重算写回 `routes.forecast_end_date`。
- Phase 3 加 `route_forecast_history` 计算预测偏差。

### 6.5 看板指标

指标定义见 [产品与功能](01-产品与功能.md) §3.7；技术实现注意：

- abandoned 不进分母；skipped 进分母不计完成；postponed 计入原计划日、新 occurrence 计入新计划日。
- 无实际分钟时按计划分钟估算并标注。
- 路线进度按 task 去重；累计活跃天数不是连续打卡。
- 指标必须能和今日页/DB 对账；口径变更要写版本记录。

### 6.6 代码静态评审（Phase 2，方案 A）

**输入**

- 代码文本/文件、语言。
- 题目来源/难度/标签。
- 自测结果（通过数/失败用例/未测）。
- 用户自报复杂度。
- 是否独立完成。
- 思路说明（可选）。

**Rubric**：维度与权重见 [产品与功能](01-产品与功能.md) §3.9；本节只定义技术输入/输出/硬规则。

**输出**

```json
{
  "score": 76,
  "level": "B+",
  "confidence": 0.82,
  "dimensions": {
    "correctness_risk": { "level": "medium", "score": 62 },
    "complexity": 80,
    "quality": 74,
    "testing": 60,
    "communication": 70
  },
  "evidence": [
    { "file": "solution.py", "line": 12, "quote": "for i in range(n):", "issue": "未处理空数组" }
  ],
  "strengths": ["哈希表思路正确"],
  "improvements": [
    { "action": "补空数组/重复元素边界", "how": "加 2 个用例", "verify": "自测通过" }
  ],
  "followups": ["数组有序时能否用双指针？复杂度？"],
  "not_evaluated": ["runtime_time", "hidden_tests"]
}
```

**硬规则**

- 不执行代码；不声称 AC/正确。
- 正确性展示为“静态风险低/中/高 + 自测通过率”。
- 没有证据的维度标 `not_evaluated`，不给分。
- 证据必须包含文件/行号/片段。
- 改进 ≤3 条，必须可执行。
- 评审失败/超时保留提交，允许重试。
- Prompt 注入防护：代码和题目按不可信数据处理。
- 记录 `ai_runs` 与 `rubric_version`。

**不做**：沙箱、代码运行、隐藏测试、性能实测、CLI/Git/IDE。

### 6.7 复习调度（Phase 3）

```json
{
  "first_review_after_days": 1,
  "intervals": [1, 4, 7, 14],
  "max_interval_days": 60,
  "reset_on_wrong": true
}
```

- 首次复习：学习后第 2 天。
- 之后 +1/+4/+7/+14，对应第 3/7/14/28 天。
- 答对升一阶段；答错回退一阶段并次日重现。
- 答对低置信度重复当前阶段；高置信度进下一阶段。
- 超过最后阶段：倍率 + 上限，进入长期复习。
- 每日配额：min(到期数, 10 题) 且 ≤35% 容量。
- 积压优先级：overdue_days×2 + lapses×3 + stage_weight + goal_relevance。
- 复习日期以实际完成时间为基准。

### 6.8 能力聚合（Phase 3）

- 目标岗位能力要求：`target_level` + `weight`。
- 证据来源权重：代码 1.0、工程 1.0、八股/项目 0.8、自评 0.3、外部测评 0.6。
- 时间衰减半衰期 30 天。
- 证据数 ≥3 且置信度 ≥0.5 才算 assessed。
- readiness 只在 assessed 上加权；展示证据覆盖率；覆盖率 <50% 低置信度。
- 无证据 → unassessed，不显示 0 分。
- 快照用于 7/30 天趋势；预测历史用于偏差。

### 6.9 周总结

- 周日 20:00（用户时区）。
- 内容：完成率、完成任务数、实际分钟、活跃天数、顺延率、类型分布、路线进度、预测日期、下周重点、规则建议。
- Phase 1 只发企微消息，不做完整周报页面。

## 7. 通知系统

### 7.1 渠道

Phase 1 只支持企业微信群机器人。

- 配置：群机器人 Webhook → 设置页粘贴 → 测试发送 → 配置时间/免打扰/事件。
- 未配置渠道不发推送，今日页/看板仍可用。

**Webhook 安全**

- 只允许 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=...`。
- 校验 scheme/host/path；禁止重定向；超时 10s；响应 ≤64KB。
- key 加密存储；日志脱敏；接口只返回 masked。
- 支持重新配置/删除/测试。

### 7.2 事件与模板

事件、默认时间和触发条件见 [产品与功能](01-产品与功能.md) §3.8。技术侧去重键：

```text
morning:{date}
evening:{date}
overdue:{date}
carry_over:{date}
weekly:{iso_week}
```

模板变量：`{date} {weekday} {planned_tasks} {completed_tasks} {completion_rate} {planned_minutes} {actual_minutes} {carry_count} {forecast_date} {focus} {today_link} {dashboard_link}`。

### 7.3 偏好与免打扰

- 按事件配置：开关、时间、渠道、免打扰行为、时区。
- 默认：早报 07:30、晚报 20:30、周总结周日 20:00；免打扰 23:00–07:00。
- 早报/晚报/周总结延迟到静默结束；逾期/顺延可丢弃。

### 7.4 Outbox

- 业务事务只写 `notification_outbox`；Worker 异步发送。
- 唯一键 `(user_id, dedup_key)`；重试 1/5/30 分钟；3 次后 dead。
- `dead` 可在设置页查看并手动重发。
- 企微 `errcode != 0` 视为失败，记录 `errmsg`。

### 7.5 限制

- 群机器人单向推送，不能读回复。
- 不支持个人私聊。
- 消息长度/频率按企微官方限制；系统内合并/截断。
- Markdown 语法适配；链接必须完整 URL。

## 8. 安全、隐私与运维

### 8.1 认证与授权

- 密码 Argon2id。
- Access Token 30 分钟，放响应体，由前端保存在内存；Refresh Token 30 天，`HttpOnly` Cookie（`Path=/api/v1/auth`、`SameSite=Lax`、生产 `Secure`），数据库只存哈希。
- Refresh 每次轮换；已撤销 token 被重放时，撤销该用户全部活跃 refresh token。
- `/auth/refresh`、`/auth/logout` 校验 `Origin` 白名单，拒绝跨站 Cookie 写操作。
- 所有业务查询带 `user_id`；Phase 1 只有 `user` 角色。
- 登录限流 5 次/分钟/IP；5 次失败锁定 15 分钟。
- Phase 1 不做邮箱验证/密码找回；后续补。

### 8.2 数据隔离

- 每张业务表有 `user_id`。
- Repository 强制注入当前用户；禁止前端传 `user_id` 过滤。
- 集成测试覆盖越权访问。

### 8.3 文件、导入与 AI 授权

- 只允许 `.md`/`.markdown`，5MB，UTF-8；MIME sniffing。
- 文件名不参与存储路径；UUID。
- 对象存储服务端加密；访问用短时签名 URL。
- 首次导入前取得 `ai_import` 同意；记录 scope/version；撤销后停止新导入。
- 导入内容按不可信数据处理；HTML 后续必须清洗脚本/样式。
- AI Prompt 用分隔符与指令层级；禁止把计划内容当指令。
- AI 请求只发送必要上下文；不默认保存全文；`ai_runs` 存 hash/加密快照。

### 8.4 Webhook SSRF

- 只允许 HTTPS + `qyapi.weixin.qq.com` + 固定 path。
- 禁止重定向、内网 IP、`file://`/`gopher://`。
- 超时 10s；响应 ≤64KB。
- key 加密、日志脱敏、支持轮换/删除。

### 8.5 密钥与日志

- JWT secret、加密 key 从环境变量/Secrets Manager。
- 日志不输出密码、Token、Webhook、完整计划/代码。
- 审计：导入确认、路线调整、通知配置变更、批量删除。
- PII 脱敏：姓名/手机/邮箱/公司/学校可配置。

### 8.6 备份与迁移

- MySQL 每日全量 + binlog；保留 7 天。
- 对象存储版本化/生命周期。
- Alembic 迁移；发布前 staging 演练；失败回滚。
- 备份恢复演练每季度。

### 9.2 关键测试

1. 结构化 Markdown：3 阶段/6 周/42 任务 → 解析 ≥80%。
2. 半结构化：只有周计划/无日期 → 按容量分配并标 assumption。
3. 混乱 Markdown：AI 失败/低置信度 → 保留原文，允许手动。
4. 重复确认 → 只创建一次路线。
5. 回滚 → 路线归档/删除，原路线不受影响。
6. 今日生成重复 → 一条 daily_plan，occurrence 不重复。
7. 完成 → 看板完成率/实际分钟更新。
8. 延期 → 次日 occurrence，旧实例 postponed，postpone_count+1。
9. 连续延期 3 次 → 提示拆分/放弃。
10. 预测：剩余 600，吞吐 120 → 6 天（含 10% buffer）。
11. 通知 dedup → 只发一次；失败重试 → dead。
12. Webhook 非白名单 → 422，不发请求。
13. 用户 A 访问 B → 404/403。
14. 时区：上海/洛杉矶的今日与顺延日期正确。
15. Phase 2：无自测结果 → 正确性只给静态风险，不给正确性分。
16. Phase 2：证据不足 → `not_evaluated`，不编造。

### 10.4 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| Markdown 格式差异 | 导入成功率低 | 规则 + AI + 预览编辑；先支持模板 |

| AI 成本失控 | 不可持续 | 分级模型、缓存、预算、异步 |
