组件名称为建议。各模块样式使用 CSS Modules/明确领域前缀和既有 token；不复制 `prototype.css`，不叠加无边界全局覆盖。依赖 P2 已验证的异步任务组件、字段错误、鉴权客户端与测试基础，不另建平行实现。

### 3.2 状态归属

| 状态 | 权威来源/恢复方式 |
| --- | --- |
| 路线生成任务、草案内容/版本、锁定集合、可确认性 | 服务端；URL 保留任务/草案定位信息 |
| 题目、已提交答案、反馈、追问、会话完成数 | 服务端；按业务日期恢复，当前浏览题序不等于完成数 |
| 错题原始回答、本次回忆、评级、阶段、到期日、配额 | 服务端独立资源；不能用新答案覆盖原答案 |
| 复习配置、默认配置、旧阶段映射与调度预览 | 服务端版本；表单可本地编辑，最终预览/保存以响应为准 |
| 能力分、置信度、覆盖率、准备度、证据有效性/衰减 | 服务端评估版本；前端不推算 |
| 抽屉、筛选、选中题目、过程摘要展开 | React/URL/UI 偏好；与敏感业务数据分离 |
| 可选计时的逐秒显示 | 本地显示，服务端起点/暂停状态校正；到期不自动提交 |

所有含简历/代码/答案的 AI 内容均按文本安全渲染，不使用原型 `innerHTML` 拼接业务内容；不默认落浏览器永久存储。AI 授权分别覆盖代码评审、路线生成、回答反馈，不能复用单一导入授权冒充同意。

服务端不可用时保留输入并展示错误/重试，不能套用原型的固定诊断、定时进度、静态到期日或能力分。测试演示与真实用户路径隔离。

## 4. 实施顺序与依赖

推荐顺序：**契约 → 提问 → 错题读取 → 复习设置 → 复习会话/容量 → 路线生成 → 能力证据 → 综合验收**。

原因：提问先产生可追溯回答与错题；设置/预览先明确复习规则再运行会话；能力看板最后接入多来源证据。路线生成可在后端已交付时与复习链并行，但单个执行任务不交叉修改共享导航/样式。

## 5. 不可遗漏的业务规则

### 5.1 提问/复习

- 每日题默认 4 道但渲染服务端实际 3–5 道，不硬编码题目数组；同一天重复进入恢复会话。
- 计时可暂停，默认 10 分钟仅作产品默认；服务端时间校正，非逐秒请求。到期仅提醒，答案仍可编辑/提交。
- 展开答案前保留本次回忆，展开后才允许评级；评分结果必须等服务端成功再进入下一题，避免原型固定延时跳题丢失上下文。
- 答错回退一级并次日重现；不确定保持；确定进阶。最终阶段/已掌握语义以后端定约为准；前端不写死 next_date。
- 默认 `[2,3,7,14,28]` 是**阶段间隔**，不是累计“第几天”。原型时间线文字有累计日期歧义，实施前统一为“间隔 N 天/预计到期日”，到期日取后端。
- 间隔 1–365 严格递增整数；题数 1–100，容量百分比 1–100。每日默认最多 10 题且最多今日容量 35%，两项限制同时生效。
- 配额、跨日、错题去重、并发评级由服务端保证。前端在冲突后拉取最新状态并说明，不直接重放旧写操作。

### 5.2 路线生成

- 生成和确认不覆盖执行中路线。确认只创建新草稿；后续激活走已有路线动作并独立确认影响。
- `12 周 × 120 分钟 × 80% = 134.4 小时` 仅作验收样例；72 项/108 小时可用、96 项/144 小时超出 9.6 小时需阻止确认。生产实际工作量按后端任务分钟汇总，不固定每项 1.5 小时。
- 改每日时间、周期、强度必须同步更新服务端预览、阶段分配和确认摘要。请求乱序时不得显示过期预览；预览未完成不能确认。
- 锁定与调整都带资源版本，已有锁定阶段在重生成中保持内容/顺序。确认前重新校验最新版本/容量。
- 求职平台仅固定 URL 新窗口跳转，使用 `noopener noreferrer`，不带简历/答案/账户参数，不声称已集成账户。

### 5.3 能力证据

- 代码/工程、回答、自评、外部测评来源权重分别为 1.0、0.8、0.3、0.6；30 天半衰期仅作后端规则说明，前端展示返回结果，不自行计算评估。
- 少于 3 条有效证据或置信度低于 0.5 返回未评估；分数为空，不当 0 分，不进入准备度。
- 示例准备度 70、覆盖率 60%、已评估 5/11、有效证据 19 是四个不同统计；覆盖率不是 5/11。必须读取服务端统一评估版本。
- 源记录定位到提交/评审/回答/任务的具体版本；失败评审不能伪造成有效评分证据。来源无权查看、撤回或失效时显示受限/失效状态，不暴露内容。
- P2 分数不直接等于 P3 能力分；自评/外部测评若开放录入，注明用户填报、未经平台核验。

## 7. 验收计划

### 7.1 三条必须通过的链路

1. 提问：恢复今日会话 → 保存/提交文字回答 → 反馈与追问 → 错题去重 → 回忆/展开 → 三档评级 → 下次到期与今日容量对账 → 刷新恢复。
2. 路线：输入/授权 → 异步诊断 → 草案 → 改容量/强度 → 锁定/局部调整 → 冲突或超容量阻断 → 用户确认 → 新草稿 → 原执行路线保持不变。
3. 能力：P2 评审/回答/工程产出 → 后端证据归集 → 一致评估版本 → 准备度与覆盖率 → 证据抽屉 → 原记录版本；不足/失效显示未评估或缺口。

### 7.2 状态与自动化

- 所有页覆盖加载、空、错误、进行中、成功、禁用、校验失败；按需补资源不存在/越权、限流、授权撤回、过期版本、超时/重试。
- 单元/组件验证字段校验、空值呈现、URL 状态、请求乱序丢弃、计时暂停/归零、结果状态映射。调度/能力算法在后端验证，前端用契约夹具验证显示和动作限制。
- Playwright 覆盖上述三链、键盘操作、刷新/离页重进、长文本、重复点击、断网/慢响应；真实联调验证幂等、越权、跨日/时区、多标签冲突和今日容量一致。
- UI 基线：`1280×720`、`584×761`；补测 `1440×900`、`390×844` 和 1100/860/640/420 附近。桌面第二列、侧栏/正文滚动、移动目录/底栏、抽屉内容/按钮都需实际验证。
- 对证据抽屉、危险确认检查焦点陷阱/恢复、Esc、可访问名称、锁滚动及背景阻断；触控≥44px；reduced-motion 后最终内容可读。
- P1/P2 回归：登录注册入口保持、今日容量/动作、导入/路线历史、代码快照/评审进度、看板各区块相互隔离。
- lint → build → typecheck → 自动化测试 → `git diff --check` 顺序验证，记录结果与浏览器证据，不将构建通过等同布局验收。
