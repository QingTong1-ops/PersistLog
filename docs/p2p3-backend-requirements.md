# 恒序 persistLog · P2 / P3 后端功能接口需求

- **版本**：v0.1
- **更新日期**：2026-11-15
- **适用阶段**：P2 代码反馈、P3 反馈与记忆
- **设计依据**：[P2 / P3 页面原型](../design/p2p3/README.md)、[前端技术架构](architecture.md)
- **文档目的**：说明前端页面需要后端提供的接口能力、输入输出和业务约束，供后端拆分模型、任务与 OpenAPI 契约。

本文不规定具体 URL、HTTP 方法、框架、数据库或消息队列。接口名称只表示一项业务能力，不是路由定义。实际字段命名和状态码由后端在 OpenAPI 中补充，但不得削弱本文的可追溯、权限、幂等和状态约束。

原型中的数据均为演示数据，不是生产默认值或接口返回样例。前端不得自行计算评审分数、路线容量、复习阶段或能力结论。

## 1. 范围与优先级

### 1.1 P2 必须交付

1. 代码提交草稿、代码快照、提交历史和提交详情。
2. 创建异步评审、查询进度、查看结果、失败重试和评审历史。
3. 评分、代码证据、扣分依据、改进项和复盘追问。
4. 改进项完成状态、追问回答的持久化。
5. 近 7 天 / 30 天代码提交、评分、自测和改进统计。

### 1.2 P3 必须交付

1. 背景诊断、路线草案生成、容量预览、局部调整、阶段锁定和用户确认。
2. 每日文字提问、回答反馈、追问、会话恢复和错题生成。
3. 错题库、到期复习、掌握结果、间隔重复和每日容量调度。
4. 复习设置读取、校验、预览、保存和恢复默认。
5. 能力概览、未评估状态、证据列表及证据来源追溯。

### 1.3 明确不在范围内

- 不执行用户代码，不提供 AC 判定，不运行隐藏测试。
- 不测量真实运行时间或内存，不建设代码沙箱。
- 不接入 CLI、Git、IDE 或求职平台账户，不自动抓取外部测评。
- 不提供语音作答。
- 不把一次代码评分直接当成能力分。
- 不向前端返回或伪造 Agent 的逐字内部思维链。
- 不让 AI 直接替换执行中的路线，也不改写已有完成记录。

## 2. 通用接口约定

### 2.1 身份、归属与权限

- 复用 P1 的登录、刷新、用户档案、时区和 AI 授权体系，不另建用户体系。
- 所有业务数据按当前用户隔离。列表、详情、任务进度、重试、草稿、统计和证据查询都必须校验归属，不能只依赖前端隐藏入口。
- 从 P1 今日任务或路线进入代码提交时，后端校验任务、阶段和路线确实存在且属于当前用户。
- 代码、简历、项目摘要、回答和错题均属于用户私有数据，不能出现在公开缓存、公开文件地址或其他用户的统计中。

### 2.2 通用响应要求

- 资源返回稳定的唯一标识、创建时间、更新时间；可修改资源还需返回版本号，用于乐观并发控制。
- 时间戳使用带时区的明确格式；日期、星期、到期日和“今天”按用户时区计算。后端需记录并返回本次计算采用的时区或业务日期。
- 数值未产生、证据不足和不适用使用空值及明确状态表达，不能用 `0` 代替。
- 空列表正常返回，并附空态原因或下一步建议所需的信息；空数据不等于接口失败。
- 列表支持稳定排序和分页。筛选后的条数与列表使用同一条件，页面总数不能仅在当前页累加。
- 统计、评分、调度和能力结论由服务端返回，前端不按演示公式重算。
- 后端提供稳定的枚举值及展示所需信息，前端不依赖中文文案判断状态。

### 2.3 错误、幂等与并发

- 统一返回机器可读错误码、可读说明、请求追踪标识；表单错误还应定位到具体字段。
- 至少区分：参数错误、未认证、无权限、资源不存在、状态冲突、版本冲突、授权缺失、配额或服务限流、AI 暂不可用、内部错误。
- 对可重试错误明确返回是否可重试；不能把所有失败都提示为“网络异常”。
- 创建提交、创建评审、保存回答、提交复习结果、生成及确认路线等写操作支持幂等键。相同请求重发不能生成重复提交、重复评审或重复错题。
- 修改草稿、路线草案和复习设置时携带资源版本。版本过期返回冲突，不能静默覆盖另一页面的修改。
- 同一提交已有运行中的评审时，不允许重复启动另一个评审；重试应返回当前任务或明确冲突。
- AI 服务超时不能丢失已保存的用户内容。后台 worker 异常退出后，任务可恢复或进入可重试的失败态，不能永久停留在“处理中”。

### 2.4 异步任务通用模型

代码评审、路线生成、局部调整及耗时较长的回答反馈可复用统一任务模型，至少提供：

- 任务标识、业务类型、关联业务资源、当前状态、进度、当前阶段、可公开的过程摘要。
- 创建时间、开始时间、完成时间、最后更新时间、失败原因、是否可重试。
- 结果资源标识或结果版本；结果尚未产生时明确为空。
- 过程步骤包含顺序、名称、状态、开始 / 结束时间和简短说明，例如“已读取多少行代码”“正在对照用户自测”。
- 过程摘要只说明实际读取范围、处理步骤和结论依据；不得用固定延时编造百分比、步骤或“思考过程”。
- 后端不能确定百分比时返回阶段和空进度，不强制补一个虚假的数字。单次任务进度不应无故倒退。
- 提供任务状态查询能力；可增加实时订阅，但订阅与查询必须遵循同一状态模型，断线后可重新拉取并恢复。

建议将“任务执行状态”和“业务评估状态”分开：

- 执行状态：等待处理、处理中、成功结束、失败。
- 代码评估状态：未产生、已评分、证据不足。
- 路线生成状态：未产生、草案已生成、生成失败。

这样可以表达“评审流程成功结束，但因没有自测而不给总分”，无需伪造一种执行失败。

## 3. P2 · 代码反馈

### 3.1 代码练习首页

| 接口能力 | 输入需求 | 返回需求与约束 |
| --- | --- | --- |
| 获取代码练习概览 | 可选统计范围，默认近 30 天 | 下一项代码任务、提交数、平均分、最高分、改进项完成数、待完成改进；统计数据与看板使用同一口径 |
| 获取当前代码任务上下文 | 可选今日任务、路线任务或阶段标识 | 题目、来源、路线 / 阶段、预计时长、难度、允许语言、任务说明、验收产出；没有关联任务时支持自由练习 |
| 获取提交历史 | 评审显示状态、分页、排序；支持全部、待评审 / 评审中、已评审、证据不足、失败 | 提交标识、题目、时间、语言、来源、最新评审标识和状态、评审次数、最新评审得分（无评分时为空）、自测摘要；每条记录均有可访问的详情标识 |
| 获取待完成改进 | 默认按最近未完成排序，支持分页 | 改进项标识、所属提交与评审、标题、验证方式、完成状态、后续提交关联；不能返回已经失效的其他用户数据 |

“当前代码任务”应与 P1 今日任务关联，但代码提交不能自动把 P1 任务标记为完成；任务完成仍走已有任务动作。

### 3.2 草稿与代码提交

| 接口能力 | 输入需求 | 返回需求与约束 |
| --- | --- | --- |
| 保存代码草稿 | 题目、语言、难度、来源上下文、标签、代码文本、文件名、自测、复杂度、思路；关联任务可选 | 草稿标识、内容版本、保存时间；刷新或重新进入后可恢复 |
| 获取最近草稿 / 指定草稿 | 草稿标识或当前用户 | 完整表单内容、来源上下文、版本；从旧提交复制时返回新草稿，不允许修改旧快照 |
| 删除草稿 | 草稿标识、版本、幂等键 | 删除结果；正式提交后对应草稿可清理，但不得删除正式提交 |
| 创建代码提交并开始评审 | 完整题目与代码快照、自测与复杂度、独立完成确认、代码 AI 授权、幂等键；可关联原提交和改进项 | 提交标识、首次评审任务标识、初始状态、创建时间、详情所需信息；提交保存成功后再返回，不能只返回一个未持久化的任务号 |
| 从旧提交复制为待修改草稿 | 原提交标识 | 原代码和说明的副本、来源提交标识；明确这是新提交，不覆盖原记录 |

**代码与表单校验：**

- 支持 Python 3.11、Java 17、JavaScript、TypeScript；语言集合及版本由后端统一维护。
- 前端可能先读取本地文本文件，后端接收的是代码文本与文件名，不需要接收或执行原始二进制文件。
- 单份文本代码上限为 200 KiB；限制文件名长度和扩展名，拒绝不支持的语言、空代码、空题目和非法长度。只按文本处理，不拼接 shell 命令或执行文件。
- 保存原始代码和换行，返回代码行数与只读快照；文件名、行号、代码片段用于后续证据定位。
- 难度为简单、中等、困难或未标记；标签去重并限制数量、长度。来源展示文本与关联资源标识分开保存。
- 时间复杂度和空间复杂度必填，代表用户自己的判断，不是系统实测；可选思路需要与代码一起进入本次快照。
- 自测分为“已提供”和“尚未自测”。已提供时：通过数为非负整数，总数为正整数，通过数不能大于总数，失败用例可选；尚未自测时不保留伪造的通过数或总数。
- 必须记录独立完成确认和代码静态评审授权的版本、用途、时间。未授权时不得把内容发送给第三方 AI，但可保留未提交的本地表单。

**快照不可变：**正式提交后，代码、自测、复杂度、题目上下文和授权范围不可被后续编辑覆盖。修改代码必须创建新提交，可关联原提交；重新评审同一快照则创建新评审记录。

### 3.3 异步评审与历史

| 接口能力 | 输入需求 | 返回需求与约束 |
| --- | --- | --- |
| 获取提交详情 | 提交标识，可选评审标识；默认最新评审 | 不可变代码快照、语言、题目上下文、自测、复杂度、思路、当前评审摘要；待评审、失败和未评估也必须能读取代码 |
| 获取最新评审进度 | 提交标识或评审任务标识 | 通用异步任务信息、读取范围、过程步骤、最新更新时间、结果状态；可离开页面后恢复，不靠浏览器计时推进 |
| 获取评审结果 | 提交标识与评审标识 | 本次评审的结果、评分、证据、改进项、追问、生成信息；默认最新，查看旧评审时不能混入最新结果 |
| 重试评审 | 原提交标识、失败或可重试的评审标识、幂等键 | 新评审标识、递增的评审序号和初始状态；使用原代码快照，不覆盖旧失败和旧评分 |
| 获取本次提交的评审记录 | 提交标识、分页 | 每次评审的序号、状态、时间、耗时、失败原因、是否有评分、结果入口；最新记录有明确标识 |
| 获取其他提交历史 | 当前提交标识、分页 | 与提交历史相同的数据结构，支持在详情页直接切换，不返回当前用户的越权数据 |

- 提交和评审是一对多关系。提交先持久化，首次评审随后入队，二者需要在同一业务操作中可靠完成。
- 显示状态至少覆盖：待评审、评审中、已评审、证据不足、评审失败。
- “未自测”是提交属性；“证据不足”是评审结束后的评估结果。未自测的提交仍需经过处理流程，不能创建后立即伪装成已完成。
- 失败时保留提交、失败步骤和可重试原因。重试只追加评审，不增加一条相同代码提交。
- 最新评审失败时，不能把旧成功评审的分数标成最新分数；旧分数可在指定历史评审中查看。
- 刷新、重新登录或换设备后，均可通过提交标识恢复最新进度和结果。
- 结果生成后，详情查询与统计查询应能观察到一致的评审版本，不能出现详情已更新而列表长期保留旧状态。

### 3.4 评审结果、证据与改进

评审结果至少包含：

| 数据 | 后端需要保证的内容 |
| --- | --- |
| 总体结果 | 总分、等级、置信度、静态风险、评估状态、模型 / 规则版本、完成时间；没有评分时相关字段为空并给出原因 |
| 评分维度 | 正确性风险、复杂度、代码质量、测试与验证、表达与复盘；每项包含分数或未评估状态、说明、扣分依据 |
| 代码证据 | 文件名、起止行号、代码片段、问题描述、严重程度、建议；证据必须属于本次提交快照，行号有效 |
| 改进方向 | 最多 3 项，每项包含标题、具体改法、验证方法、可选代码证据、完成状态 |
| 复盘追问 | 围绕同一份代码的问题列表，问题标识、顺序和上下文；不能换成与代码无关的通用题 |
| 过程摘要 | 接收上下文、读取快照、静态分析与自测对照、整理评分与证据等真实可公开步骤 |

**评分约束：**

- 已提供自测时，也只能把自测作为用户声明的证据，不宣称已通过系统判题。
- 未提供自测时，可保留静态风险和其他有依据的建议，但正确性分数、总分和等级不评定；不能把未评估写成 `0` 分。
- 待评审、失败、证据不足不进入平均分和最高分。
- 评分、等级、风险和置信度由后端评审规则或模型结果生成，前端不按固定权重补算。
- 演示中的 `76`、`B+`、`0.82` 及五项维度只用于页面联调，不得作为缺省评分或评分公式。

**后续写操作：**

| 接口能力 | 输入需求 | 返回需求与约束 |
| --- | --- | --- |
| 更新改进项完成状态 | 改进项标识、完成 / 未完成、版本；可关联处理它的新提交 | 最新状态、完成时间、关联提交、统计影响；由用户主动确认，AI 不得自动标记完成 |
| 保存复盘追问回答 | 提交标识、评审标识、追问标识、文字回答、幂等键 | 回答标识、保存时间、原问题与代码上下文；可用于每日提问和错题来源，不覆盖原评审 |
| 获取复盘追问及回答 | 提交与评审标识 | 问题、已有回答、保存状态；查看旧评审时返回对应版本的回答 |

### 3.5 代码趋势与看板区块

提供按近 7 天或近 30 天查询的代码统计能力，支持后续扩展明确日期范围。

返回：

- 时间范围、时区、提交总数、有效评分提交数、平均分、最高分、改进项完成数 / 总数。
- 按时间分组的评审平均分、自测通过率、提交数；日期与数值序列一一对应。
- 最近提交列表，与代码练习历史使用同一详情标识和状态模型。
- 无评分日期或无自测日期返回空点，不补 `0`，不把不同指标的天数强行对齐后虚构数值。
- 提交数统计实际提交；平均分、最高分和评分趋势仅统计有效评分；自测通过率仅统计用户提供了自测的提交。
- 改进统计来自持久化的用户标记，不由代码评分变化推断。同一提交多次重试的统计去重规则由后端统一实现。
- 空范围返回可展示的空态与零计数，平均分和最高分为空；统计失败不能影响 P1 执行看板其他区块。

## 4. P3 · 诊断与路线生成

### 4.1 接口能力

| 接口能力 | 输入需求 | 返回需求与约束 |
| --- | --- | --- |
| 创建诊断与路线草案 | 目标岗位、目标日期、每日分钟、周期周数、简历 / 项目摘要、当前困境、路线生成 AI 授权、幂等键 | 生成任务、输入摘要、初始状态；用户内容先保存，AI 失败后可恢复和重试 |
| 查询生成进度与结果 | 生成任务标识 | 通用异步状态、诊断结果或失败原因、草案标识；可刷新恢复 |
| 获取路线草案 | 草案标识 | 原始输入、诊断、容量、阶段 / 周 / 任务结构、锁定状态、调整记录、草案版本、确认状态 |
| 调整草案参数并预览 | 草案标识、每日分钟、周期、强度 / 任务侧重、锁定阶段、草案版本 | 新草案版本、容量预览、阶段分配、确认摘要、风险和可确认状态；不能只在前端修改显示值 |
| 局部调整一个阶段 | 草案标识、目标阶段、调整要求、锁定集合、版本、AI 授权、幂等键 | 调整任务、更新后的阶段和新草案版本；未调整及已锁定阶段保持不变 |
| 设置阶段锁定状态 | 草案、阶段、锁定 / 解锁、版本 | 最新锁定集合与版本；已锁定阶段不能被 AI 或容量重排自动改写 |
| 校验并准备确认 | 草案标识、版本 | 最新容量、目标可行性、是否可确认、阻断原因、影响摘要 |
| 用户确认并创建路线草稿 | 草案标识、版本、确认标识、幂等键 | 新路线草稿标识、来源草案和版本、创建时间、路线状态；不自动启用 |

### 4.2 生成与容量规则

- 主流程必须是：背景与目标 → 诊断 → 草案 → 调整 → 用户确认。AI 输出不能绕过草案和用户确认进入今日计划。
- 诊断需区分已有基础、优先补足、表达重点，并引用用户输入中的依据；输入不足时返回补充信息要求，不编造经历。
- 草案保留阶段、周、任务层级，以及任务标题、类型、预计分钟、产出、验收标准、关联能力；每周需有可验收产出和复盘 / 缓冲安排。
- 默认容量基准为：周期天数 × 每日分钟 × 80% 有效容量。每日分钟、周期、有效容量、任务预计工作量均由后端计算并返回，前端只展示。
- 原型默认 12 周、每日 120 分钟、80% 有效容量，对应 134.4 小时；这是校验示例，不是所有用户的固定配置。
- 总预计工作量由各任务预计分钟求和，不能长期把每项固定为 1.5 小时；原型仅以此简化演示。
- 总工作量超过容量时返回超出量及降低强度、延长周期、缩小范围等建议，禁止确认；仅禁用前端按钮不算校验。
- 目标日期与所选周期、每日投入不匹配时明确提示可行性，不能静默缩短任务或超出目标日期。
- 局部调整必须保持锁定阶段内容和顺序不变；返回调整记录，便于比较调整前后差异。
- 草案更新必须产生新版本。生成和确认都不得覆盖执行中路线，也不改写历史任务完成记录。
- “确认草案”只创建一份新的路线草稿，不等于激活路线。后续启用需复用 P1 路线动作并进行独立确认，明确对当前路线的影响。
- 撤回 AI 授权后禁止新的生成或局部调整，但不删除用户已经确认的草案和路线。

## 5. P3 · 每日文字提问

### 5.1 提问会话

| 接口能力 | 输入需求 | 返回需求与约束 |
| --- | --- | --- |
| 获取或创建今日提问 | 用户业务日期，可选路线 / 目标上下文、幂等键 | 会话标识、题目数、来源构成、作答进度、计时配置、题目列表、已有回答与反馈 |
| 获取提问会话详情 | 会话标识 | 当前题、全部题目状态、回答、反馈、追问、是否完成；支持刷新和跨设备恢复 |
| 保存回答草稿 | 会话、题目、回答、版本 | 保存状态和时间；保存草稿不等于提交，不触发反馈或错题 |
| 提交题目回答 | 会话、题目、非空文字回答、可选作答耗时、幂等键 | 原回答、真实反馈、需要补足的维度、参考要点、追问入口、是否生成错题、会话进度 |
| 获取题目反馈 | 会话、题目、回答版本 | 与该回答版本对应的反馈和追问；不能因查看下一题而丢失 |
| 获取 / 创建追问 | 原回答标识、追问序号或追问标识 | 围绕原题和回答的问题、上下文、保存状态；不是无关的新每日题 |
| 提交追问回答并获取反馈 | 追问标识、文字回答、幂等键 | 追问回答、对应反馈、必要的新错题或能力证据关联 |
| 完成 / 重新访问会话 | 会话标识 | 完成状态、已答题数、各题回顾入口；全部题作答后才完成 |

### 5.2 内容和作答规则

- 每天 3–5 道文字题，默认 4 道；从今日任务、历史错题、简历项目和目标岗位组织题目，可优先低分能力项。
- 题目包含稳定标识、类型、题干、提示、来源类型、来源资源标识和关联能力。来源不可只存一段无法追溯的展示文字。
- 同一业务日期重复进入应恢复同一会话，不能重复生成一套题；题目生成失败时保留会话并可重试。
- 回答去除首尾空白后不能为空。反馈必须基于实际回答，至少指出准确性、完整性、结构表达中需要补足的部分及理由。
- 进度按已提交的不同题目数计算，不以当前浏览位置代替；完成后允许回看题目、回答和反馈。
- 重新练习应创建新会话或新回答版本，不覆盖历史回答与证据。
- 可选计时默认 10 分钟，支持暂停和继续。后端保存开始时间、累计用时和暂停状态即可，不需要逐秒请求接口。
- 时间到只提示，不自动提交、不锁定输入、不把未提交回答算错；跨设备恢复时可依据服务端记录校正剩余时间。
- 答错或低分可生成错题，保留原题、原始回答、参考要点、问题类型、知识点和来源。去重后返回错题标识，不能每次打开反馈都重复生成。
- 低分阈值、题目来源配比和每日生成时间需形成后端可配置规则，不能散落在前端常量中。

## 6. P3 · 错题与复习

### 6.1 错题库和到期概览

| 接口能力 | 输入需求 | 返回需求与约束 |
| --- | --- | --- |
| 获取错题列表 | 知识点、问题类型、来源、到期状态、掌握状态、分页 | 错题标识、题干、来源、当前阶段、下次到期日、状态、原始回答摘要、参考要点摘要 |
| 获取错题详情 | 错题标识 | 原题、原始回答、参考要点、来源追溯、知识点、问题类型、当前阶段、下次到期日、复习历史 |
| 获取今日复习概览 | 用户业务日期，可选筛选条件 | 今日到期总数、可复习数、已完成数、剩余数、题数上限、预计分钟、可用容量、容量上限、当前复习间隔 |
| 获取复习历史 | 错题标识、分页 | 每次回答、掌握结果、前后阶段、计划与实际复习时间、下次到期计算结果 |

- 筛选至少支持知识点和问题类型，例如概念不清、边界遗漏、表达结构缺失；枚举由后端维护。
- 错题原始回答与复习时的本次回答必须分开存储，不能用新回答覆盖“当时的回答”。
- 来源可以关联每日提问、代码评审追问、工程任务等；必须能定位原记录。
- 筛选只改变显示集合，不篡改全局每日配额；概览需区分“全部到期数”和“当前筛选下可复习数”。

### 6.2 复习会话与掌握结果

| 接口能力 | 输入需求 | 返回需求与约束 |
| --- | --- | --- |
| 开始 / 恢复今日复习 | 业务日期、可选知识点和问题类型筛选、幂等键 | 复习会话、筛选后的题目顺序、进度、当前题、配额与容量；刷新后可继续 |
| 保存本次回忆回答 | 会话、错题、文字回答、版本 | 本次回答草稿、保存时间；不能覆盖原始回答 |
| 展开原始回答与参考要点 | 会话、错题 | 原始回答、参考要点、当前阶段；记录已展开状态，再允许提交掌握结果 |
| 提交掌握结果 | 会话、错题、本次回答版本、答错 / 答对但不确定 / 答对且确定、幂等键 | 本次复习记录、原阶段、新阶段、下次到期日、调度原因、剩余题数、下一题或完成状态 |
| 稍后复习 / 结束当前会话 | 会话标识 | 已保存进度、剩余题目、恢复入口；未评级题不能自动算完成 |

**调度规则：**

- 默认复习间隔为第 2、3、7、14、28 天，每个值表示从当前阶段到下一阶段的天数，不是累计时间轴。
- **答错**：阶段回退一级，首阶段保持首阶段；次日优先重现。次日重现是明确的调度覆盖规则，不能被普通新任务挤掉。
- **答对但不确定**：保持当前阶段，按当前阶段间隔安排下一次复习。
- **答对且确定**：进阶一级，按新阶段间隔安排下一次复习；最后阶段之后的掌握状态需明确返回，不能以空日期冒充 `0` 阶段。
- 每次调度都保存原阶段、新阶段、使用的间隔配置版本、用户时区、计算得到的到期日和原因。
- 重复提交同一掌握结果不重复推进阶段；不同结果或旧版本提交返回状态 / 版本冲突。
- 复习会话开始和提交结果均需检查配额与题目当前状态，防止多个标签页重复处理或越过上限。

### 6.3 每日配额与容量

- 默认每天最多 10 题，同时最多占今日学习容量的 35%，两个限制必须共同生效。
- 服务端根据今日可用分钟、容量比例和每题预计分钟决定本次可复习数量，并返回未纳入的原因。
- 超过题数或时间上限的到期题顺延，保留原到期时间和顺延原因，不能删除或标记为已掌握。
- 到期题优先于普通新任务；可选“到期优先”或“与新任务交替”，由后端生成顺序。
- 答错后要求次日重现的题需优先预留容量；若次日容量仍不足，返回明确的超额与顺延处理结果。
- 复习占用需进入 P1 今日容量统计，不另建一套与今日计划无关的分钟账。

### 6.4 复习设置

| 接口能力 | 输入需求 | 返回需求与约束 |
| --- | --- | --- |
| 获取复习设置 | 当前用户 | 间隔数组、每日题数上限、容量百分比、到期优先级、配置版本、默认配置标识 |
| 预览设置 | 尚未保存的间隔、题数、容量、优先级、预览日期 | 阶段时间线、预计每日题数和分钟、超额 / 顺延预览、受影响已有错题数；不得修改正式设置 |
| 保存复习设置 | 完整设置、配置版本、幂等键 | 新配置版本、保存时间、已有进度处理结果、新的调度预览 |
| 恢复默认设置 | 当前配置版本、幂等键 | 默认间隔、题数、容量、优先级及重排预览；真实保存后不能只在前端恢复表单 |

- 间隔必须为 1–365 天内严格递增的正整数，相邻阶段不能重复；每日题数为 1–100 的整数，容量比例为 1–100 的整数。
- 默认值为间隔 `[2, 3, 7, 14, 28]`、每日 10 题、容量 35%、到期优先。
- 服务端重复执行全部校验，不依赖前端行内错误。
- 保存时明确已有错题的阶段如何映射，不能清空历史复习记录或无意间把所有题重置为第一阶段。
- 返回设置变化对已有到期日的影响及并发冲突；配置版本需写入之后产生的复习记录。
- 间隔数量上限、最后阶段完成语义和已有进度迁移策略必须在 OpenAPI / 领域文档中明确，不能由各端自行假设。

## 7. P3 · 能力看板与证据

### 7.1 能力概览和证据查询

| 接口能力 | 输入需求 | 返回需求与约束 |
| --- | --- | --- |
| 获取能力看板 | 可选路线 / 目标、评估状态筛选；默认当前目标路线 | 路线信息、准备度、证据覆盖率、已评估 / 总能力数、有效证据数、最后评估时间、评估规则版本、能力列表 |
| 获取单项能力详情 | 能力标识、路线上下文 | 分数或未评估状态、路线权重、置信度、有效证据数、未评估原因、下一行动建议 |
| 获取能力证据列表 | 能力标识、来源类型、有效性、分页 | 来源类型、来源资源标识、发生时间、摘要、来源基础权重、时间衰减、有效权重、有效性及原因 |
| 追溯证据来源 | 证据标识 | 原始代码提交 / 评审、回答、工程任务或用户填报记录的标识与摘要；按权限返回必要内容 |
| 记录自评或外部测评（开放入口时） | 能力、来源说明、结果、发生时间、可选备注 | 用户填报证据、来源类型、未经平台核验的标识；不得伪装成自动抓取或第三方认证 |
| 请求重新评估 | 可选路线 / 能力范围、触发原因、幂等键 | 评估任务或最新评估版本；重复触发需去重，不阻塞页面读取已有结果 |

### 7.2 评估口径

- 能力目录和路线权重由后端维护，当前路线涉及的能力权重应可追溯到路线版本；不能由前端写死 11 项能力。
- 代码 / 工程证据基础权重 `1.0`，八股 / 项目回答 `0.8`，外部测评 `0.6`，自评 `0.3`。
- 证据时间衰减半衰期默认 30 天。以证据发生时间到评估时间的年龄计算：`有效权重 = 来源基础权重 × 0.5 ^ (年龄天数 ÷ 30)`。
- 后端统一评估时间、有效性、时区和舍入规则；过滤无效证据后再计算，不把用户自测通过率直接当成能力分。
- 每项能力至少 3 条有效证据，且置信度至少为 `0.5`，才可返回评估分数。未达到任一条件均为未评估。
- 未评估返回空分数、证据缺口或置信度原因，不画 0 分，也不能解释为“完全不会”。证据条数满足但置信度不足时仍需说明。
- 准备度只归一化汇总已评估能力：`Σ(能力分 × 路线权重) ÷ Σ(已评估能力路线权重)`。没有已评估能力时准备度为空，不是 0。
- 证据覆盖率为已评估能力的路线权重之和除以路线能力总权重，不是“已评估项数 ÷ 总项数”。
- 概览的有效证据数沿用原型口径，仅汇总已评估能力的有效证据；可另返回全部能力的证据数，但字段含义必须区分。
- 评估结果保留规则版本、计算时间、输入证据版本，能够解释历史结论；更新评估不能抹掉原始证据。

### 7.3 证据产生与一致性

- 代码评审完成后可形成代码证据；评审中、失败记录不能形成有效评分证据。证据不足的评审能否贡献静态代码质量证据，需要由领域规则明确，不能计入正确性能力。
- 每日提问和项目追问提交有效反馈后可形成回答证据，并关联具体回答版本，而不是只关联会话。
- P1 工程任务完成后可形成工程证据，关联任务产出和验收信息；仅打卡但没有产出时不自动视为高权重证据。
- 自评和外部测评属于用户填报，必须保留“未经外部平台核验”的来源性质。
- 证据处理使用领域事件或等价可靠机制，提交、回答和任务完成事件需要幂等消费；同一来源同一版本不能重复计数。
- 代码结果、回答或工程记录更新后，应触发相应证据与能力重算；看板读取最后完成的一致版本，不等待前端逐条计算。
- 证据失效、撤回授权或删除来源时，明确是否重算及保留哪些审计记录；不得继续返回无权访问的原始内容。

## 8. 数据关系与跨模块联动

建议至少明确以下领域对象及关系，名称可调整后端模型，但关联不能丢失：

```text
用户
├─ 代码草稿
├─ 代码提交（不可变快照）
│  └─ 多次评审
│     ├─ 评分与代码证据
│     ├─ 改进项及完成记录
│     └─ 复盘追问与回答
├─ 路线生成输入 / 诊断 / 草案版本
│  └─ 用户确认后创建路线草稿
├─ 每日提问会话
│  └─ 原题回答 → 反馈 / 追问回答 → 错题或能力证据
├─ 错题
│  └─ 多次复习记录与调度结果
├─ 复习设置版本
└─ 能力评估版本
   └─ 多条可追溯证据
```

需要后端保证的联动：

1. 创建代码提交与首次评审可靠衔接，提交历史实时反映最新任务状态。
2. 改进项完成状态影响代码统计，关联后续提交时不覆盖原评审。
3. 回答生成错题与能力证据时去重，原回答始终可追溯。
4. 错题评级、每日容量和 P1 今日计划使用同一业务日期与容量口径。
5. 路线草案确认只创建新草稿；路线能力权重与之后能力看板使用同一路线版本。
6. AI 任务完成、失败、重试和授权撤回均有审计记录，不能只有一条短暂 Toast。

## 9. 隐私、安全与可维护性

- 为代码静态评审、路线生成、回答反馈分别明确 AI 使用目的和授权范围；记录授权文本版本、时间和撤回时间，不能用一次模糊的“同意 AI”覆盖所有用途。
- 仅将完成任务所需的最小内容发送给第三方；代码快照、简历摘要、回答的提供方、用途、保留期限和删除策略需可审计。
- 日志和追踪默认不记录完整代码、简历、回答或认证信息；必要的排查样本需要受控访问和脱敏。
- 返回给前端的代码、简历、AI 文本和证据片段按纯文本数据处理；后端不得依赖 HTML 注入来实现高亮。
- AI 输出需要结构校验、长度限制、行号校验和内容安全检查；结构不合法时进入可重试失败，不保存半套“成功”评分。
- 评审结果保存模型 / 提示词 / 规则版本和必要的安全摘要，便于复现问题；不向普通用户暴露密钥、系统提示词或内部思维链。
- 对用户提交、AI 调用、重试和重新评估设置合理限流与配额；限流时保留输入并返回可重试信息。
- 统计、调度和能力计算必须有时区、夏令时、跨日、任务重试及并发测试。
- OpenAPI 还需明确每个字段是否必填、是否可空、长度、枚举、分页、排序、错误码及版本冲突行为。

## 10. 开发前必须定约的规则

以下规则无法仅从静态原型确定，后端不应擅自用演示数据补齐；需要与产品 / 前端确认后写入 OpenAPI 或领域规则文档：

| 主题 | 必须明确的内容 |
| --- | --- |
| 代码评分 | 总分与维度关系、等级区间、置信度与静态风险算法、未自测时“测试与验证”的处理；不能从示例 `76` 反推权重 |
| 趋势归属 | 按提交时间还是评审完成时间归集；重试后取哪次评分；改进项分母按创建还是完成时间归集；自测通过率按提交平均还是按用例汇总 |
| 草稿与保留 | 服务端草稿数量、过期时间、提交后的清理规则；代码和 AI 内容的保留与删除政策 |
| 题目生成 | 3–5 题的来源配比、低分入错题阈值、数据不足时的补充策略、追问轮次与长度限制 |
| 复习调度 | 最后阶段后的掌握状态、设置变更时现有阶段映射、超额顺延顺序、跨日与修改时区处理 |
| 路线生成 | 强度可选值、支持的周期范围、草案有效期 / 版本上限、目标日期与周期冲突的完整规则 |
| 能力评估 | 有效证据定义、是否要求不同来源、置信度公式、总分舍入、失效与重算触发条件 |
| 代码转错题 | 原型已有“代码评审”来源的错题，但未规定自动还是用户主动加入；需保留来源关联并确认触发方式 |
| 异步交互 | 状态查询间隔、是否提供实时订阅、超时阈值、失败重试上限、AI 部分结果的保存策略 |

这些事项不影响先建立数据模型和基础接口，但在对应规则定约前，不能把某一实现假设宣称为最终产品行为。

## 11. 联调验收清单

### 11.1 P2

- [ ] 粘贴代码和选择本地文本文件最终都形成同一份不可变代码快照；超限、空代码和不支持语言有字段错误。
- [ ] 通过数大于总数、负数、非整数均被后端拒绝；未自测不会生成虚构的通过数。
- [ ] 重复点击提交或请求重发只生成一个提交和一个首次评审。
- [ ] 提交后立即返回可访问的详情，离开再进入可看到服务端最新进度，代码始终可读。
- [ ] 待评审、评审中、成功、证据不足、失败均能从历史进入详情；空列表、任务失败有明确状态。
- [ ] 失败重试追加评审序号，旧失败仍可查；同一提交不能并发创建多个运行中的评审。
- [ ] 证据的文件名、行号、片段与本次快照一致；改进项不超过 3 条且包含验证方法。
- [ ] 未自测的正确性、总分和等级为空，不进入平均分；其他建议仍有代码依据。
- [ ] 改进标记、追问回答刷新后保留；旧评审详情不会混入新一次评审的结果。
- [ ] 近 7 / 30 天的图表、提交数、平均分、最高分和改进统计同步变化，无数据点不补 0。

### 11.2 P3

- [ ] 路线生成未授权时不调用第三方，用户输入仍保留；失败和刷新后可恢复任务。
- [ ] 容量随每日时间、周期、强度及任务预计分钟变化；超容量草案在服务端也无法确认。
- [ ] 锁定阶段在局部调整后保持不变，旧版本修改返回冲突，草案保留输入和调整历史。
- [ ] 确认只创建新路线草稿，不覆盖执行中路线或历史完成记录。
- [ ] 每日提问默认 4 题，刷新后恢复已答进度；空回答不能提交，完成后可回看原回答和反馈。
- [ ] 计时暂停、恢复和到期均不自动提交；答错 / 低分生成错题时去重且保留来源。
- [ ] 复习先保留本次回答，再展开原回答和参考要点；三种掌握结果产生正确的阶段与到期日。
- [ ] 同一掌握结果重发不会重复进阶；超额题顺延，答错题次日重现不被普通任务挤占。
- [ ] 非递增、重复、非整数、超范围复习间隔被后端拒绝；设置保存、恢复默认和已有进度处理一致。
- [ ] 复习占用与 P1 今日容量一致，用户时区跨日时不会重复生成复习或提问。
- [ ] 能力证据少于 3 条或置信度低于 0.5 时显示未评估；未评估不进入准备度、不当作 0 分。
- [ ] 准备度、覆盖率和有效证据数符合各自定义；每条证据都能追溯到来源，并展示基础权重和衰减信息。
- [ ] 任一 AI 失败、超时或返回非法结构时，原用户数据不丢失，错误可追踪，重试不会制造重复记录。

## 12. 建议的后端交付顺序

1. **契约与基础模型**：统一错误、幂等、任务状态、资源版本、用户时区和 AI 授权；先提供可联调的空态与异常态。
2. **P2 提交闭环**：草稿与快照 → 提交历史 → 异步评审 → 结果 / 证据 / 改进 → 趋势。
3. **P3 复习闭环**：提问与回答 → 错题生成 → 复习会话 → 调度 → 设置和今日容量。
4. **P3 路线闭环**：诊断任务 → 草案版本 → 容量和锁定 → 局部调整 → 用户确认。
5. **P3 能力闭环**：证据归集 → 评估规则 → 概览和证据追溯 → 与代码、提问、工程记录联动。
6. **收尾**：OpenAPI 与真实响应核对、权限与隐私检查、异步故障恢复、并发与跨日测试，再接生产前端页面。

每一步都应同时提供成功、加载 / 处理中、空数据、参数错误、无权限、失败和可重试状态，避免只联调一条理想路径。
