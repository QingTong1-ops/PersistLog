# P1 页面设计协作规范

## 1. 目的与适用范围

本规范用于后续开发者、设计者与 AI 协作，统一恒序 persistLog 前端的视觉、布局、动效、交互细节和文字内容，并明确数据真实性与验收边界。

**本规范以当前 P1 React / Next.js 实现为准。** 产品与 API 约定以 `README.md` 文档索引中的后端产品文档、OpenAPI 契约和 `docs/architecture.md` 为准；历史设计稿已从工作区清理，需要回溯时查阅 Git 历史，不要将旧描述直接复制为新实现。

主要实现入口：

- 页面结构与导航：`components/app-shell.tsx`
- 共享组件：`components/ui.tsx`
- 全局基础样式：`app/globals.css`
- 兼容样式：`app/uwp.css`
- 当前视觉覆盖：`app/optimized.css`
- 页面组件：`components/today/`、`components/dashboard/`、`components/routes/`、`components/import/`、`components/settings/`、`components/auth/`

文中“必须”是验收要求，“建议”是默认选择，“可以”是可选方案。已有实现不满足要求时，应先记录差距，不要为了文档一致而扩大改动范围。

### 快速原则

1. 先让用户看清“下一步做什么”，再展示统计和说明。
2. 复用共享组件与现有 token，不为单个页面另造一套视觉语言。
3. 所有真实用户数据都来自状态或接口；示意图必须明确标注。
4. 新页面先保证桌面和窄屏的内容顺序、可读性与可操作性，再增加装饰。
5. 同时修改结构、样式和文案，不留下相互矛盾的旧描述。

## 2. 视觉方向：静谧推进

设计应传达稳定、清晰、可追踪的执行体验。视觉重点是当前任务、完成记录和计划容量，而不是打卡压力、营销口号或技术控制台。

- **以浅色工作区为主。** 中性灰背景、白色内容面、细分隔线建立层级。
- **用有限的品牌色表达行为。** 靛蓝用于导航选中、主要操作与关键链接；青绿用于完成和正向进展。
- **先分隔，再装饰。** 优先使用留白、对齐、排版和细线，不靠厚重阴影、大面积渐变或大量彩色卡片制造层次。
- **深色只做局部品牌锚点。** `#252e52` 可用于登录品牌区、企微卡与已有路线 Hero；今日 Hero 是浅色卡片，不再使用深色大 Hero。
- **为内容留足空间。** 工作区不是多个同权重卡片的拼盘；主任务应比辅助信息更醒目。

避免：高饱和多色渐变工作区、普遍 20px 以上的卡片圆角、漂浮感很强的大阴影、无意义玻璃效果，以及用红黄色装饰普通数据。

## 3. 设计令牌与样式边界

### 3.1 当前 token

新增或调整样式优先使用以下 `app/optimized.css` 中的变量，不在组件内重复写一套近似色。

| Token | 值 | 用途 |
| --- | --- | --- |
| `--bg` | `#f4f5f7` | 工作区背景 |
| `--surface` | `#ffffff` | 卡片、侧栏与表单表面 |
| `--surface-subtle` | `#f8f9fb` | 次级区域、悬停与弱强调 |
| `--line` | `#e3e6ec` | 常规边框与分隔线 |
| `--line-strong` | `#d4d9e3` | 输入框、按钮等较强边界 |
| `--text` | `#1d2330` | 标题、正文重点与关键数值 |
| `--text-2` | `#4b5565` | 正文、次级操作 |
| `--text-3` | `#667085` | 辅助说明、元信息 |
| `--text-faint` | `#98a2b3` | 最弱层级文字；不代替可读的正文色 |
| `--primary` | `#4f5d96` | 主操作、选中与品牌色 |
| `--primary-hover` | `#414f86` | 主操作悬停 / 按下 |
| `--primary-soft` | `#eef0f8` | 品牌色浅底 |
| `--teal` | `#2f7d73` | 完成、正常、正向进展 |
| `--teal-soft` | `#edf6f3` | 完成与正向状态浅底 |
| `--amber` | `#a5662a` | 容量、延后与需注意状态 |
| `--amber-soft` | `#faf4ec` | 提醒浅底 |
| `--red` | `#a94444` | 错误与高风险操作 |
| `--red-soft` | `#fbf2f1` | 错误与危险区域浅底 |

其他要求：

- 卡片圆角基线为 `12px`，按钮、输入框等控件通常为 `8px`，标签通常为 `6px`；小图形可使用圆形或胶囊形。
- 工作区卡片阴影使用 `--optimized-shadow`。已有弹层、登录卡等可以保留与层级相符的局部阴影，不要将其推广到每张卡片。
- 图标统一使用项目已有的 `lucide-react`。保持线性和尺寸一致，装饰图标设 `aria-hidden="true"`。
- 状态不能只靠颜色区分；同时提供“已完成”“需调整”“解析失败”等可读文字。

### 3.2 样式加载与迁移

当前加载顺序为：`uwp_components/styles.css` → `app/globals.css` → `app/uwp.css` → `app/optimized.css`。后者可能覆盖前者，排查样式时必须检查最终生效规则，而不是只看组件 className。

- `--brand-600`、`--ink-600` 等旧变量已映射到 optimized token，用于兼容旧组件。新样式优先使用 `--primary`、`--text-*`、`--surface-*`。
- 不继续扩展旧 UWP 专属变量，不把原型中的 `.ring`、旧 `.app` 布局等强行套回 React 页面。
- `components/uwp-root.tsx` 的根节点同时带有 `app` 类。通用 `.app` 不能再作为工作台两列网格容器，否则可能将登录或整个工作台压入侧栏网格。工作台容器是 `.app-shell`。
- 修改共享类名前检查所有使用位置。页面私有样式使用清晰的前缀，避免用一个通用类名同时表达布局、主题和业务状态。
- 不恢复已清理的 P1 静态原型及重复预览图，P1 运行页面以 `app/optimized.css` 与 React 组件为准；历史方案可通过 Git 回溯。P2 / P3 规划原型仅在 `design/p2p3/`，使用说明见 `design/p2p3/README.md`。原型必须经过 React 实现、真实接口与浏览器验收，才能标记为已支持能力。
- 不在末尾不断叠加无边界覆盖来“修复”问题。先定位冲突来源；修改后同步清理失效注释与规则。

## 4. 排版、间距与布局

### 4.1 排版与间距

- 中文正文使用现有系统字体栈；数字使用 `--font-num`，统计值使用等宽数字 `font-variant-numeric: tabular-nums`。
- 页面主标题通常为 `28–32px`；卡片标题约 `18px`；正文基线 `14px`；辅助信息和元信息通常 `12–13px`。
- 辅助文字也要可读，不要通过不断缩小字号、降低透明度来塞进卡片。
- 标题保持短而明确；正文行高约 `1.5–1.75`。长标题允许换行，不用单行省略隐藏关键任务名称。
- 使用有限间距阶梯：`4 / 8 / 12 / 16 / 20 / 24 / 32px`。卡片内部、卡片之间和页面区块之间应有明显但不过度的层级。
- 同组控件等宽、等高、对齐；相邻内容使用 `minmax(0, 1fr)` 和 `min-width: 0` 防止长内容撑破网格。

### 4.2 工作台骨架

桌面由固定侧栏、顶栏和主文档组成；主文档负责滚动，侧栏固定在视口内，可独立纵向滚动。

| 项目 | 当前基线 |
| --- | --- |
| 桌面侧栏 | `216px` |
| `861–1200px` 侧栏 | `196px`；其中 `861–1100px` 仍沿用紧凑导航，隐藏侧栏文字 |
| 顶栏 | `60px`，显示必要的位置、日期和用户入口 |
| 主区域内边距 | 顶部 `28px`，左右 `32px`，底部 `56px` |
| 内容宽度 | `.app-main > .main > .view` 最大 `1360px`，水平居中 |
| 栅格 | 主内容列必须 `minmax(0, 1fr)`，主内容自身 `min-width: 0` |

**主内容必须占据 `.app-shell` 的第二列。** 桌面保留以下结构约束，不要让主内容自动落入固定的第一列：

```css
@media (min-width: 861px) {
  .app-shell > .app-main {
    grid-column: 2;
  }
}
```

侧栏改为 `position: fixed` 后，仍需保留它在网格中对应的列宽；不能仅通过让右侧绝对定位来“补齐”页面。`html`、`body` 防止横向溢出是保护措施，不能靠 `overflow-x: hidden` 掩盖真实的布局错误。

### 4.3 窄屏与重排

| 断点 | 行为 |
| --- | --- |
| `≤860px` | 隐藏桌面侧栏；顶部显示品牌；底部使用“今日 / 看板 / 路线 / 我的”。主内容左右 `18px`，底部预留 `88px`；指标双列，主要内容单列 |
| `≤640px` | 今日 Hero 和容量卡重排；主要按钮触控高度至少 `44px` |
| `≤560px` | 页头与操作区纵向排列，主要按钮可以全宽，表单单列；登录表单区域收紧内边距 |
| `≤420px` | KPI 改为单列；今日 Hero 操作按钮纵向全宽 |

- 窄屏不是桌面整体缩小，而是按“标题 → 核心状态 → 主操作 → 详细内容”的顺序重排。
- 导航、提交按钮、关闭按钮等触控目标建议至少 `44×44px`。视觉上较小的图标按钮要有足够点击区域。
- 不隐藏完成核心任务所需的内容。装饰性示意图可以隐藏，真实进度、表单和错误信息不能隐藏。
- 基线视口是 `1280×720` 与 `584×761`；新增 `1440px`、`390px` 或其他尺寸验收时，应记录实际验证结果，不把建议尺寸写成已验证尺寸。

## 5. 页面与组件规则

### 5.1 页头

使用 `PageHeader` 统一页面标题、必要短说明和右侧操作。页头只回答“这是哪里、可以做什么”，不要堆叠 eyebrow、阶段徽标、重复标题或多段产品愿景。

每个区块只保留一个主操作。次级操作使用描边或文字样式，不与主操作争夺注意力。

### 5.2 今日

- Hero 是浅色主任务卡：进度环 + 下一任务标题 / 类型 / 时长 + 主次操作。
- 完成状态通过真实进度、勾选与任务文字共同表达，不靠庆祝动画或压力文案。
- 独立容量卡展示真实的已排时间、每日容量和缓冲。三者来自同一份状态或接口数据，弹窗和主页面不得写死不同数值。
- 容量不足时给出可执行的下一步，例如移出、拆分任务或调整每日容量；不要只显示红色警告。
- 任务行以任务名称为主体，类型、预计时长与状态为辅助。列表用分隔线而不是每行一张浮起的小卡片。

### 5.3 看板、路线与设置

- 看板展示执行数据与真实趋势，不展示后续能力占位卡、无来源增长率或虚构设备在线信息。
- 图表提供时间范围、单位和文字解释；颜色是辅助编码，不能成为唯一的信息来源。
- 路线页优先表达阶段、任务与版本关系，避免把技术字段名直接作为用户标题。
- 设置按“档案与容量、通知、授权、数据与账号”等用户任务分组。技术细节若确有必要，折叠展示，不与常用设置争夺首屏。
- 高风险操作与普通设置分区，明确对象、影响与不可逆后果；危险按钮不与安全的主保存按钮并列争抢注意力。

### 5.4 登录与注册

- 桌面采用左右结构：左侧品牌主张与 `AuthPlanPreview` 产品示意卡，右侧登录 / 注册表单。
- 左侧只保留一句明确主张和短解释，不堆功能列表、虚构评价、名言或营销指标。
- 示意卡表达“计划 → 执行 → 进展”的关系，必须标注“产品示意”。其示例任务和固定进度不得冒充真实用户统计。
- 深墨蓝品牌底与局部柔和光晕只属于品牌区，表单区保持浅色、简洁和高可读性。
- 表单保留密码显隐、提交中状态和字段区域内的错误提示。提交中防止重复操作，同时保留清晰的按钮状态。
- `≤860px` 隐藏大型示意卡，保留品牌标识和简洁标题，让表单尽快进入视野；不额外添加循环动图或视频。

### 5.5 共享组件

优先复用 `components/ui.tsx` 中的 `Button`、`Tag`、`StatusBadge`、`ProgressBar`、`ProgressRing`、`Modal`、`Sheet`、`ConfirmDialog`、`Toast`、`PageHeader`，而不是复制近似实现。

- `ProgressRing` 使用 `.progress-dial` 与 `.progress-dial__center`，通过 `--ring-track` / `--ring-color` 配主题；不要再套旧 `.ring`。
- 图标按钮必须有能说明动作的 `aria-label`，如“关闭页面地图”“显示密码”，不能只有“按钮”或文件名。
- Toast 用于短时操作反馈，默认 `3.8s`；不能承载必须阅读的长说明、表单错误或高风险确认。
- 当前 `Modal` 基于 `ContentDialog`；`Sheet` 已处理 Esc 与锁定页面滚动。不得据此宣称所有弹层都已有完整焦点陷阱、焦点恢复或 Esc 支持。
- 新增或修改弹层时，实际验证标题关联、Tab 顺序、焦点陷阱与恢复、Esc、背景交互和锁滚动；缺什么就记录什么，不以视觉相似代替可访问性验证。

## 6. 动效与操作反馈

动效只解释“内容从哪里来、状态发生了什么变化、操作是否被接收”，不做持续吸引注意的装饰。

### 当前基线

| 动效 | 时长 / 方式 |
| --- | --- |
| 登录示意卡入场 | `.55s ease-out`，轻微上移并淡入 |
| 登录示意进度 | `.75s ease-out` |
| 登录示意勾选 | `.3s ease-out` |
| 登录示意路线轨迹 | `1.1s ease-out`，一次性绘制 |
| 提交中 spinner | `.7s linear infinite`，仅在真实等待期间显示 |
| 进度环数值变化 | `stroke-dashoffset .45s ease` |
| 普通过渡 | 建议 `.18–.26s`，用于颜色、边框、淡入或小范围位移 |

规则：

- 入场位移保持约 `8–12px`，不做大面积飞行、连续弹跳、背景视差或循环闪烁。
- 不用无依据的数字跳动、假进度条或动画速度暗示系统性能。
- 加载动画必须由真实 pending 状态驱动；请求结束、成功或失败后立即退出该状态。
- 完成操作的反馈应轻量，保持页面位置和阅读上下文稳定。
- `app/globals.css` 已在 `prefers-reduced-motion: reduce` 下将动画与过渡压至 `0.001ms`。新增动效不得绕过该规则；关闭动画后仍应显示最终状态和完整内容。

## 7. 细节、表单与状态

- 保留清晰的 `:focus-visible` 轮廓；不能只设置 `outline: none`。输入框可使用品牌色边框与浅底焦点环。
- 表单标签在输入前可见，占位符只提供格式示例，不代替标签。
- 字段错误在相应字段区域行内展示，使用 `role="alert"`；错误文本要指出如何修正，不要只弹 Toast。
- 按钮具备默认、悬停、按下、焦点、禁用和提交中状态；禁用不能只靠降低透明度，也要阻止操作。
- 弹层与抽屉有明确标题和关闭入口，内容过高时让内容区域可滚动，避免操作按钮被截断。
- 空状态说明“现在没有什么”与“下一步能做什么”，提供一个主要行动；不放大段产品教程。
- 加载状态保持原有布局尺寸，避免加载完成后内容突然跳动。
- 错误状态保留用户已填写内容，并允许重试或返回；不因一次失败清空无关工作。
- 数字配合单位与统计周期，例如“近 7 天完成 12 项”“每日容量 120 分钟”，不要裸写“12”“95”让用户猜测。
- 日期、分钟、百分比、任务数必须由真实数据派生。零值与空数据正常展示，不用示例值补齐空白。

## 8. 文字内容与数据真实性

### 8.1 写作语气

使用直接、克制、面向行动的中文。像产品在与用户协作，不像开发日志、营销页或 AI 在自我解释。

- 标题短，先给结论或动作，例如“今日计划”“调整每日容量”。
- 说明只在帮助理解后果、作出选择或完成任务时保留；能由标题和控件表达的内容不重复解释。
- 同一名称保持一致：使用“今日计划、任务、完成记录、预计完成日期”，不混用“今日 occurrence”“执行实体”等术语。
- `occurrence`、`over_capacity`、状态机表达式、Token 存储、Provider Stub、路由参数与“正式版应……”等开发语言不直接出现在普通用户界面。
- 开发预览、状态演示和调试入口应与普通产品内容隔离，不能以“产品说明”的名义长期留在主流程。
- 不使用“坚持打卡”“失败惩罚”“加油”等制造压力的措辞，也不使用空泛的“AI 智能分析”“全方位赋能”等承诺。
- 未实现的真实能力评估、AI 功能和自动化能力不能写成已存在；必要规划标注“尚未开放”，但不要反复展示开发阶段广告。

### 8.2 示例

| 场景 | 推荐 | 避免 |
| --- | --- | --- |
| 估算说明 | 根据剩余工作量和近期完成速度估算。 | AI 深度洞察你的未来，精准预测一切。 |
| 撤销影响 | 撤销后不能导入新计划，已有路线和任务不受影响。 | 点击这里执行撤销相关操作。 |
| 容量提醒 | 已超出 30 分钟，建议移出或拆分任务。 | 你今天又失败了，请继续努力！ |
| 表单错误 | 密码至少 8 位，请补充后再提交。 | 参数不合法 / Token Provider 异常。 |
| 空状态 | 今天还没有任务，可以从学习路线添加。 | 暂无数据，敬请期待更多精彩。 |
| 开发状态 | 代码练习尚未开放。 | Provider Stub 已挂接，等待 P2 联调。 |

### 8.3 数据与示意边界

- 登录后的任务、时间、进度、统计和通知必须来自当前用户状态或后端响应，不硬编码“看起来合理”的数字。
- 演示数据只在明确演示场景出现，并显著标注“产品示意”或“演示”。不要在真实登录后用示例卡冒充用户统计。
- 不使用虚构用户评价、无来源名言、无依据增长百分比、设备状态或“已有多少人使用”等社会证明。
- 示意图的数据可以固定，但文案和图形的含义必须一致，例如 3 项任务完成 1 项只表示约三分之一，不暗示真实完成率。
- 高风险操作的后果说明不是冗余文案，不能为了“去 AI 味”删掉。优先删除重复问候、自我描述和同义反复。
- 如果接口缺少某项数据，隐藏该模块、说明不可得或展示真实空状态；不得用前端常量伪造完整结果。

## 9. 协作与变更流程

1. **先读实现。** 查看对应 React 组件、共享组件、最终 CSS 和数据来源，确认是结构问题还是覆盖问题。
2. **限定范围。** 只修改相关页面和共享规则；共享规则变更时检查所有调用方，不顺手重排无关页面。
3. **对齐规范。** 使用已有 token、断点、共享组件和中文术语；确需偏离时，在变更说明中记录原因。
4. **同步内容与状态。** 检查加载、空、错误、完成、禁用、提交中和危险确认，不只交付静态成功态。
5. **实际验收。** 在浏览器验证桌面与窄屏，使用真实操作路径检查布局、键盘、反馈与数据一致性。

推荐验证命令：

```bash
pnpm lint
pnpm typecheck
pnpm build
git diff --check
```

页面基线视口为 `1280×720`、`584×761`。涉及布局时还应检查 `860px`、`640px`、`420px` 附近的重排，以及长标题、零值和真实大数据量。

### 提交前检查清单

#### 视觉

- [ ] 主操作、当前任务和关键数据是否一眼可辨？
- [ ] 是否复用了当前色板、圆角、阴影、图标与控件？
- [ ] 是否出现不必要的大渐变、厚阴影、彩色卡片或重复装饰？

#### 布局

- [ ] 桌面主内容是否确实位于 `.app-shell` 第二列？
- [ ] 内容是否完整可见，而非靠裁切或隐藏溢出掩盖问题？
- [ ] 窄屏导航、表单、按钮、弹层和底部留白是否可用？
- [ ] 长文本、长数字和空数据是否不会撑破网格？

#### 动效与细节

- [ ] 动效是否解释状态，且由真实状态触发？
- [ ] 减少动态效果偏好是否生效？
- [ ] 键盘焦点、按钮名称、字段错误和状态文字是否可理解？
- [ ] 弹层是否实际验证了焦点、Esc、锁滚动与背景行为，而非假定支持？

#### 文字与数据

- [ ] 是否删除了开发口吻、重复说明和无依据宣传？
- [ ] 必要的后果、限制和修正方法是否保留？
- [ ] 数字是否有来源、单位和统计周期？
- [ ] 示例是否标注“产品示意 / 演示”，并与真实用户数据隔离？

#### 工程

- [ ] 上述检查命令是否在与交付一致的工作区通过？
- [ ] 浏览器是否走过用户实际操作路径，而不只是确认页面能打开？
- [ ] 历史注释和文档是否仍描述旧行为？若在本轮变更范围内，是否已同步？

## 10. 当前边界

P1 的设计重点是稳定的执行闭环与可信的信息表达，不是补齐未来所有产品模块。后续阶段新增功能时沿用本规范的基础语言，再补充对应页面规则，不以历史原型中的占位内容作为实现承诺。

规范不是对尚未验证功能的背书。深色主题、完整移动端适配、复杂图表、完整弹层键盘管理等能力，只有在对应实现和验收完成后才能标记为已支持。
